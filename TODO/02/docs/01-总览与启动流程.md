## 2. `main()` 启动时序（逐步拆解）

启动大致分 **7 个阶段**，每一阶段的失败策略都不同（有的 `return 0`，有的只打日志继续）。

```
 main(argc, argv)
   │
 ①├─ [Linux] 特权环境清洗 + 能力(capability)分配与降权
   │    · getauxval(AT_SECURE) 判断是否 setuid 运行
   │    · platf::sanitize_process_environment()  清掉危险环境变量
   │    · kms::ensure_privileged_drm_worker_started()  ← 先起特权 DRM 线程
   │    · drop_elevated_privileges(false)  ← 保留 CAP_SYS_NICE 给 EGL
   │    · egl::ensure_privileged_egl_worker_started()
   │    · drop_elevated_privileges(true)   ← 彻底降权
 ②├─ [macOS] 把 cwd 锚定到 Contents/MacOS，使 ../Resources/assets 可用
 ③├─ [Windows] SetDefaultDllDirectories(APPLICATION_DIR|SYSTEM32) → 防止 PATH 劫持
   │    setlocale(LC_ALL, "C")
   │
 ④├─ mail::man = make_shared<safe::mail_raw_t>()    ← 全局消息总线（“邮箱”）
   │    config::parse(argc, argv)                    ← 解析 sunshine.conf，失败直接 return 0
   │    logging::init(min_log_level, log_file)
   │    ── 从这里开始日志才进日志文件 ──
   │    BOOST_LOG(info) << PROJECT_NAME << version << commit
   │    log_publisher_data() / log_config_settings()
   │
 ⑤├─ 子命令分发：config::sunshine.cmd.name → cmd_to_func
   │      creds / help / version / restore-nvprefs-undo
   │      （有子命令则执行完直接返回，不启动服务）
   │
 ⑥├─ display_device::init(appdata()/"display_device.state", config::video)
   │      ↑ 顺便做崩溃后的显示配置恢复（guard 必须最先创建、最后析构）
   │    [Windows] nvprefs：restore undo 文件 → 改应用 profile → 改全局 profile → unload
   │    [Windows] SetProcessShutdownParameters(0x100, SHUTDOWN_NORETRY)  ← 注销时尽量晚退
   │    [Windows] 隐藏窗口线程 session_monitor（接收 WM_ENDSESSION / 控制台关闭）
   │
   │    task_pool.start(1)                      ← ★ 1 个线程的任务池（输入回调串行化）
   │    注册 SIGINT / SIGTERM（10 秒强杀看门狗 + 通知托盘 + 释放显示 guard）
   │    [Windows] SetConsoleCtrlHandler(ConsoleCtrlHandler, TRUE)
   │    proc::refresh(config::stream.file_apps) ← 扫描应用列表文件
   │
 ⑦├─ 核心初始化（失败只记日志，**继续启动**，以便用户能进 WebUI 修配置）
   │      platf::init()                平台层（采集/输入/音频子系统的生命周期锚）
   │      proc::init()                 应用进程管理
   │      reed_solomon_init()          ★ FEC 初始化（必须在使用 FEC 前）
   │      input::init()                输入子系统
   │      input::probe_gamepads()      探测手柄（失败仅 warning）
   │      video::probe_encoders()      ★ 探测可用编码器（失败 error）
   │      http::init()                 ← 失败即 fatal + return -1
   │           · 生成/加载 TLS 证书与私钥（config::nvhttp.cert/pkey）
   │           · 加载 WebUI 账号密码（credentials_file）
   │           · 若为 FRESH_STATE：证书落到临时目录并生成新 unique_id
   │
   │    异步并行：platf::publish::start()   ← mDNS 广播
   │              upnp::start()             ← UPnP 端口映射
   │
   │    ┌─ std::jthread httpThread    { nvhttp::start }       GameStream
   │    ├─ std::jthread configThread  { confighttp::start }   WebUI
   │    └─ std::jthread rtspThread    { rtsp_stream::start }  RTSP
   │        [Windows] 若 port==47989 且检测到 GFE 的 GameStream 仍开启 → 打印致命提示
   │
   │    托盘：system_tray::init_tray[_threaded]()
   │    mainThreadLoop(shutdown_event)
   │        · Windows：托盘在独立线程，主循环直接 shutdown_event->view() 阻塞
   │        · Linux/macOS：主循环里跑 system_tray::process_tray_events()
   │
   └─ 退出：httpThread.join / configThread.join / rtspThread.join
            task_pool.stop() / task_pool.join()
            [Windows] nvprefs 还原全局 profile
            return lifetime::desired_exit_code
```

### 关键设计点

| 设计 | 原因 |
|------|------|
| 大部分初始化失败**只记日志不退出** | 保证 WebUI 仍可访问，用户能自己改回可用配置 |
| `display_device_deinit_guard` 第一个创建 | `unique_ptr` 逆序析构 → 它最后释放，保证关流时显示器配置一定被还原 |
| `task_pool` 只有 1 个线程 | 输入注入路径必须串行，避免键鼠事件乱序；也用于延迟任务（按键重复、手柄 BACK 超时） |
| `reed_solomon_init()` 在 `input::init()` 之前 | FEC 表需在任何编码/推流前建好 |
| 三个服务各自一个 `jthread` | 用 `shutdown_event->view()` 做统一退出编排；`jthread` 析构自动 join |

### 一次串流在各层之间的“角色”

| 层 | 一次串流里它负责什么 | 生命周期 |
|----|---------------------|---------|
| L0 | 启动/销毁全局资源，把 `shutdown_event` 传下去 | 进程级 |
| L1 | 鉴权、应用列表、参数下发、会话建立 | 进程级（服务器长期存活） |
| L2 | 会话状态机、三通道收发、超时与清理 | 每客户端一次（`broadcast_ctx` 是进程内共享） |
| L3 | 抓帧、编码、FEC、发包；输入注入 | 每会话一个捕获/编码循环 |
| L4 | 具体 API 调用 | 由 L3 驱动 |

## 4. 端口与地址映射

端口全部由 `net::map_port(offset)` 计算：`mapped = config::sunshine.port + offset`（越界仅 warning，范围校验在 `config.cpp` 里，`[1024 + nvhttp::PORT_HTTPS, 65535 - rtsp_stream::RTSP_SETUP_PORT]`）。

| 服务 | 偏移常量 | 值 | 默认端口（基端口 47989） | 协议 |
|------|---------|:--:|:----------------------:|------|
| GameStream HTTPS | `nvhttp::PORT_HTTPS` | −5 | **47984** | TCP/TLS |
| GameStream HTTP | `nvhttp` 基端口 | 0 | **47989** | TCP |
| WebUI HTTPS | `confighttp::PORT_HTTPS` | +1 | **47990** | TCP/TLS |
| 视频流 | `stream::VIDEO_STREAM_PORT` | +9 | **47998** | UDP |
| 控制通道 | `stream::CONTROL_PORT` | +10 | **47999** | UDP (ENet) |
| 音频流 | `stream::AUDIO_STREAM_PORT` | +11 | **48000** | UDP |
| RTSP 会话建立 | `rtsp_stream::RTSP_SETUP_PORT` | +21 | **48010** | TCP |

> `net::get_bind_address(af)` 决定绑定地址（默认 `0.0.0.0` 或 `::`）；`net::get_effective_address_family()` 在双栈模式下如果用户配了 IPv4 绑定地址，会自动把地址族收窄为 IPv4，保证 socket 协议与绑定端点一致。

## 5. 全局“邮箱”机制（为什么各模块能解耦）

`globals.h` 定义了一个进程级 `mail::man`（`safe::mail_raw_t`），并用宏 `MAIL(x)` 生成字符串常量：

```cpp
// src/globals.h
namespace mail {
  extern safe::mail_t man;
  // 全局
  MAIL(shutdown);            ///< 进程退出信号
  MAIL(broadcast_shutdown);  ///< 推流线程组退出信号
  MAIL(video_packets);       ///< 编码后的视频帧队列（跨会话共享！）
  MAIL(audio_packets);       ///< 编码后的音频包队列（跨会话共享！）
  MAIL(switch_display);      ///< 请求切换显示器
  // 每会话（通过 session->mail 获取）
  MAIL(touch_port);          ///< 触摸区域/旋转信息
  MAIL(idr);                 ///< 请求 IDR 帧
  MAIL(invalidate_ref_frames);///< 请求参考帧失效
  MAIL(gamepad_feedback);    ///< 力反馈（主机→客户端）
  MAIL(hdr);                 ///< HDR 模式变化
}
```

三个语义层次：

| 邮箱 | 作用域 | 谁发 | 谁收 |
|------|--------|------|------|
| `mail::video_packets` / `audio_packets` | **全局** | `video::capture` / `audio::capture` | `videoBroadcastThread` / `audioBroadcastThread` |
| `session->video.idr_events` 等 | **每会话** | 控制线程（客户端请求） | `encode_run` 编码循环 |
| `session->input.*` | **每会话** | 控制线程 | `task_pool` 上的输入处理函数 |

> **注意**：视频/音频包队列是**全局**的，但只有一个活跃捕获循环在往里写；`broadcast_ctx` 的 4 个线程负责消费。这也是为什么 Sunshine 同一时刻只支持一个串流会话。

## 6. 一次投屏的端到端数据流

前面 §2 讲的是「进程怎么起来」，这里讲「数据怎么流动」：先看静态的线程/套接字布局，再看一次会话从点击到关流的动态走向，最后把**每一跳的数据形态**和**反向通道**列成表。逐阶段时序（含源码位置）见 [02 §4](./02-协议与会话生命周期.md#4--首次客户端连接--推流--断开完整时序)。

### 6.1 静态视图：谁在跑

| 归属 | 线程 | 何时创建 | 职责 |
|------|------|---------|------|
| 进程级服务 | `httpThread` / `configThread` / `rtspThread` | `main()` 第 ⑦ 阶段 | GameStream HTTP(S) / WebUI / RTSP 三个 TCP 服务 |
| 广播层（全局唯一，`broadcast_ctx_t`，[src/stream.cpp:470](../../../src/stream.cpp#L470)） | `recv_thread` | `start_broadcast()` | UDP 收包与 PING 匹配（`recvThread`，[src/stream.cpp:1423](../../../src/stream.cpp#L1423)） |
| 同上 | `control_thread` | 同上 | 控制通道 ENet 轮询 + 反馈/HDR 下发（`controlBroadcastThread`） |
| 同上 | `video_thread` | 同上 | 从 `mail::video_packets` 取编码包 → 分片/FEC → UDP 发送 |
| 同上 | `audio_thread` | 同上 | 从 `mail::audio_packets` 取 Opus 包 → 4+2 FEC → AES-CBC → UDP 发送 |
| 每会话 | `session.videoThread` | `session::start()` | 采集 → 编码 → 投递到全局 `mail::video_packets` |
| 每会话 | `session.audioThread` | 同上 | 音频采集 → Opus → 投递到全局 `mail::audio_packets` |
| 全局任务池 | `task_pool`（1 个线程） | `main()` 第 ⑥ 阶段 | 输入注入串行化、延迟任务（按键重复、BACK 长按超时） |

> 采集/编码循环与发送线程是**解耦**的：中间隔着一个全局邮箱队列（§5），所以编码阻塞不会直接卡住 UDP 发送节奏，但队列溢出就是丢帧的直接来源（[05 §5.1](./05-FEC-重传-丢帧与心跳.md#51-唯一的丢帧来源mailvideo_packets-溢出)）。

### 6.3 逐跳的数据形态

| 通道 | 跳 | 形态 | 关键变换 |
|------|----|------|---------|
| 视频 | ① 采集 | GPU 纹理 / 共享句柄 → `AVFrame`（NV12 / P010） | DXGI、WGC、KMS/X11/Wayland、AVFoundation（[06 §2](./06-采集与编码.md#2-视频采集管线)） |
| 视频 | ② 编码 | H.264 / HEVC / AV1 码流 | NVENC / AMF / QSV / VAAPI / VT / AVCodec；码控参数来自客户端（[04](./04-码率控制与QoS.md)） |
| 视频 | ③ 投递 | `video::packet_t` 进全局队列 | 队列满则整队清空 = 丢帧 |
| 视频 | ④ 分片 | 按 `packetsize` 切成若干 payload shard | 每帧最多 4 个 RS 块，超限整帧跳过 FEC（[05 §2.2](./05-FEC-重传-丢帧与心跳.md#22-帧级分块一个帧最多-4-个-rs-块)） |
| 视频 | ⑤ 封包 | + RTP 头（含 `fecInfo` 位域）→ 可选 AES-GCM | IV 按帧/包递增（[08 §3.4](./08-附录-协议常量与结构速查.md#34-加密与-iv)） |
| 视频 | ⑥ 发送 | UDP 数据报（≈ `packetsize`） | 按帧做 pacing，避免突发挤爆链路（[04 §6](./04-码率控制与QoS.md#6-帧内发包配速pacing)） |
| 视频 | ⑦ 客户端 | FEC 重组 → 解码 → 渲染 | 恢复失败则请求 IDR（[05 §4.1](./05-FEC-重传-丢帧与心跳.md#41-客户端驱动的恢复)） |
| 音频 | ① 采集 | 48 kHz PCM 采样帧 | WASAPI / PulseAudio（[06 §3](./06-采集与编码.md#3-音频子系统)） |
| 音频 | ② 编码 | Opus 码流 | 固定 4+2 FEC 分片，跨多个音频包（[05 §3](./05-FEC-重传-丢帧与心跳.md#3-音频-fec固定-42)） |
| 音频 | ③ 发送 | RTP（payload type `97`，FEC 包 `127`）→ AES-CBC → UDP | **不配速**，因为包小且均匀 |
| 控制 | 双向 | `NV_*_PACKET` / `control_*` 结构 → 可选加密信封 → ENet | ENet 负责可靠有序；信封见 [03 §3.1](./03-输入系统.md#31-两条输入协议0x0206-与-0x0001的分层剥离) |

### 6.4 反向通道一览

同一根 ENet 控制通道上跑着**双向**消息，方向靠报文类型区分：

| 方向 | 消息 | 触发者 | 说明 |
|------|------|--------|------|
| 客户端 → 主机 | 输入报文（键盘/鼠标/触摸/笔/手柄） | 用户操作 | `input::passthrough()`（[03 §1.1](./03-输入系统.md#11-正向通道输入注入)） |
| 客户端 → 主机 | `IDX_REQUEST_IDR_FRAME` | 解码失败/首次请求 | 置位 `idr_events`，编码循环下一帧出 IDR |
| 客户端 → 主机 | `IDX_INVALIDATE_REF_FRAMES` | 丢包导致参考帧不可用 | 失效指定帧号区间 |
| 客户端 → 主机 | `IDX_LOSS_STATS` | 客户端统计上报 | **只记日志**，不驱动码率自适应（[08 §12](./08-附录-协议常量与结构速查.md#12-易误解结论速查)） |
| 主机 → 客户端 | 力反馈 / LED / 扳机 / 运动（6 种 `control_*`） | 游戏调用 XInput | 经 `feedback_queue` → `send_feedback_msg()`（[03 §1.2](./03-输入系统.md#12-反向通道手柄力反馈)） |
| 主机 → 客户端 | HDR 模式变化 | 显示器/系统切换 | `hdr_queue` → `send_hdr_mode()` |
| 主机 → 客户端 | 终止通知（`control_terminate_t::ec = 0x80030023`） | 主机侧结束会话 | 客户端据此优雅退出而不是当作掉线 |

> 客户端的 PING 与主机的反馈是**两条独立的路**：`pingTimeout` 只由控制通道上的任意事件刷新，力反馈的下发与它无关（[05 §6.1](./05-FEC-重传-丢帧与心跳.md#61-机制-a控制通道-enet-超时保活判定)）。

## 8. 小结

- 项目是**单进程、多线程**结构：3 个网络服务 + 广播层 4 个线程（`recv` / `control` / `video` / `audio`）+ 每会话 2 个会话线程 + 1 个任务池线程。
- 层与层之间靠 **`platf::` 接口（L3↔L4）** 和 **`safe::mail_t` 邮箱（L2↔L3）** 解耦。
- 启动阶段的“宽容策略”（失败只记日志）是为了让 WebUI 始终可达。
- 端口都由 `config::sunshine.port` 偏移而来，改一个基端口即可整体搬家；UPnP/mDNS 会自动跟随。
