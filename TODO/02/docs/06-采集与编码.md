## 0. 两条链路的整体形状

```
视频链路
┌──────────────────────────── video::capture() ─────────────────────────────┐
│                                                                           │
│  [采集线程] "video::capture" / "video::capture_sync"                       │
│     platf::display_t::capture(...)      ← L4：DXGI/WGC/KMS/X11/…           │
│        │  push_captured_image_callback                                     │
│        ▼                                                                  │
│     safe::event_t<shared_ptr<img_t>>  images   ← 单槽事件（覆盖式，隐式丢帧）│
│        │                                                                   │
│  [编码线程] "video::encode" 或与采集同线程                                  │
│        │  encode_run() 主循环                                              │
│        ▼                                                                  │
│     session->convert(img)  →  encode(frame_nr, …)  ← NVENC / AVCodec       │
│        ▼                                                                  │
│     mail::video_packets  (queue_t，容量 32)                                │
└───────────────────────────────────────────────────────────────────────────┘
        │
        ▼  stream::videoBroadcastThread（见 05 篇）：FEC → 加 RTP 头 → 配速 → 加密 → UDP

音频链路
┌──────────────────────────── audio::capture() ──────────────────────────────┐
│  [采集线程] platf::mic_t::sample()   ← L4：WASAPI / PulseAudio / CoreAudio  │
│        ▼                                                                   │
│     sample_queue_t samples (32)                                            │
│  [编码线程] "audio::encode"  encodeThread()                                │
│        ▼  opus_multistream_encode_float()                                  │
│     mail::audio_packets  (queue_t，容量 32)                                │
└───────────────────────────────────────────────────────────────────────────┘
```

**一句话**：视频采集成一个「最多持有 1 帧」的事件槽，编码线程取走一帧编码成一个包塞进 32 深的队列，随后由 `stream.cpp` 的广播线程负责网络化。

## 1. 编码器子系统

### 1.1 `encoder_t`：编码器的能力描述（[video.h:290](../../../src/video.h#L290)）

`encoder_t` 不是编码器实例，而是一份**静态的能力清单**，用于探测与选择：

| 成员 | 含义 |
|------|------|
| `name` | 编码器名，配置里用（`nvenc` / `quicksync` / `amdvce` / `vaapi` / `vulkan` / `videotoolbox` / `software` / `mediafoundation`） |
| `platform_formats` | 该编码器接受的**内存类型**（`mem_type_e`）与该平台上的像素格式映射，见 [video.h:193](../../../src/video.h#L193) |
| `av1` / `hevc` / `h264` | 三个 `codec_t`，各自记录能力与选项 |
| `flags` | 编码器级能力位，见下表 |

**`encoder_t::flag_e`（[video.h:296](../../../src/video.h#L296)）**

| 标志 | 含义 |
|------|------|
| `PASSED` | 该编码器通过验证 |
| `REF_FRAMES_RESTRICT` | 需要限制最大参考帧数 |
| `DYNAMIC_RANGE` | 支持 HDR（10-bit 4:2:0） |
| `YUV444` | 支持 4:4:4 |
| `DYNAMIC_RANGE_YUV444` | 支持 4:4:4 HDR |
| `VUI_PARAMETERS` | 编码器不会在 SPS 中写 VUI 参数（如 AMD + VAAPI），需外部处理 |
| `MAX_FLAGS` | 计数哨兵 |

`encoder_t::from_flag()` 提供稳定的日志字符串，探测结束后会逐位打印 `debug` 级能力表（[video.cpp:3446](../../../src/video.cpp#L3446) 起）。

**`codec_t`（[video.h:362](../../../src/video.h#L362)）** 每个编码器对每种编码格式各持一份：

```cpp
struct codec_t {
  std::vector<option_t> common_options;    // 所有模式通用
  std::vector<option_t> sdr_options;       // SDR 4:2:0
  std::vector<option_t> hdr_options;       // HDR 4:2:0
  std::vector<option_t> sdr444_options;    // SDR 4:4:4
  std::vector<option_t> hdr444_options;    // HDR 4:4:4
  std::vector<option_t> fallback_options;  // 首选模式不可用时的回退
  std::string name;                        // 传给后端的 codec 名（如 "h264_nvenc"）
  std::bitset<MAX_FLAGS> capabilities;     // 该 codec 上的能力位
};
```

`operator[]` 让调用方可以像读数组一样读/写能力位：`encoder.hevc[encoder_t::DYNAMIC_RANGE]`。
`codec_from_config(config)` 按 `config.videoFormat` 分发：`0 → h264`、`1 → hevc`、`2 → av1`，未知值会打日志并回退到 H.264。

### 1.2 编译期编码器清单与**顺序即优先级**

各编码器在 [video.cpp](../../../src/video.cpp) 中定义，然后被收集进一个**有序**向量（[video.cpp:1471](../../../src/video.cpp#L1471)）：

| 定义行 | 变量 | 构建条件 |
|:------:|------|---------|
| [716](../../../src/video.cpp) | `nvenc`（DXGI 直连路径，Windows） | `_WIN32` 且非 Apple |
| [758](../../../src/video.cpp) | `nvenc`（AVCodec + D3D11VA 路径） | 非 Apple |
| [883](../../../src/video.cpp) | `quicksync` | `_WIN32` |
| [997](../../../src/video.cpp) | `amdvce` | 非 Apple |
| [1112](../../../src/video.cpp) | `mediafoundation` | `_WIN32` |
| [1176](../../../src/video.cpp) | `software` | 总是编译 |
| [1253](../../../src/video.cpp) | `vaapi` | Linux / FreeBSD |
| [1317](../../../src/video.cpp) | `vulkan` | Linux/FreeBSD 且 `SUNSHINE_BUILD_VULKAN` |
| [1395](../../../src/video.cpp) | `videotoolbox` | `__APPLE__` |

`encoders` 向量在 Windows 上的实际顺序是：

```
nvenc → quicksync → amdvce → mediafoundation → software
```

Linux：

```
nvenc → vulkan → vaapi → software
```

macOS：

```
videotoolbox → software
```

> **这个顺序就是自动选择时的优先级**。`software` 永远排最后，是「保底可用」选项。

### 1.3 编码器探测：`video::probe_encoders()`（[video.cpp:3286](../../../src/video.cpp#L3286)）

进程启动阶段第 7 步调用（见 [01-总览与启动流程.md](./01-总览与启动流程.md)）。算法流程：

```
probe_encoders()
  │
  ├─ allow_encoder_probing()  ── Windows 上若没有活动的显示设备 → 直接返回 -1
  │                             （原因：此时探测 DXGI 会锁死/破坏资源，见 video.cpp:64）
  │
  ├─ 已有 chosen_encoder 且 !ALWAYS_REPROBE 且 !platf::needs_encoder_reenumeration()
  │     → 直接 return 0（复用上次结果，避免每次会话都重新探测）
  │
  ├─ 重置状态：chosen_encoder = nullptr；active_hevc_mode / active_av1_mode
  │             从 config::video 重新加载
  │
  ├─ 路径 A：用户指定了 encoder（config::video.encoder 非空）
  │     └─ 在列表中找到同名项 → validate_encoder()
  │           成功 → chosen_encoder = 它（即使不满足用户要求的 codec，也照样选它）
  │           失败 → 从列表里**整体删除**
  │
  ├─ 路径 B：仍未选中，且用户要求 HEVC/AV1（active_hevc_mode >= 2 或 active_av1_mode >= 2）
  │     └─ 按顺序遍历，跳过「不支持目标 codec / 不支持所需 HDR 组合」的编码器
  │           跳过条件（mode 语义见下表）
  │
  └─ 路径 C：仍未选中 → 按顺序遍历，第一个 validate_encoder 通过的就是它
        └─ 选中后 adjust_encoder_constraints_hevc/av1() 修正 mode
```

**HEVC / AV1 mode 语义与降级**（`adjust_encoder_constraints_*`）：

| mode | 含义 | 编码器不满足时 |
|:----:|------|---------------|
| 0 | 不使用该 codec | — |
| 2 | 允许该 codec | 警告 `does not support HEVC/AV1 on this system` → mode 降为 **0** |
| 3 | 要求 **Main10 / HDR(4:2:0)** | 同上降为 0 |
| 4 | 要求 **Rext10_444（4:4:4）** | 同上降为 0 |
| 5 | 要求 **Main10 Rext10_444（4:4:4 HDR）** | 同上降为 0 |

设计取舍被明确写在注释里：**「If we can't satisfy both the encoder and codec requirement, prefer the encoder over codec support」**——宁可用这个编码器降级到非 HDR，也不为了 HDR 换一个跑不起来的编码器。

全部路径都失败时：

```
Unable to find display or encoder during startup.
  ├─ 配置里指定了 adapter_name 或 output_name → 提示检查手动选择的 GPU/显示器是否连接且通电
  └─ 否则                                    → 提示检查显示器是否连接且通电
return -1   ← 致命，进程退出
```

成功后导出三个**跨会话复用**的探测结论（[video.cpp:3437](../../../src/video.cpp#L3437)）：

- `last_encoder_probe_supported_ref_frames_invalidation` ← 决定下发的 `ref-frames-invalidation` 能力（即客户端能否用 RFI 代替 IDR）
- `last_encoder_probe_supported_yuv444_for_codec[3]` ← 每种 codec 的 4:4:4 支持，用于 `serverinfo` 能力上报

### 1.4 `validate_encoder()` / `validate_config()`

`validate_encoder`（[video.cpp:3088](../../../src/video.cpp#L3088)）对候选编码器做「真跑一帧」的实测：按 `encoder.platform_formats->dev_type` 枚举可用显示器，逐个 `platf::display(...)` + `validate_config(...)`，任一组合成功即通过。

`validate_config`（[video.cpp:3024](../../../src/video.cpp#L3024)）的检查清单：

| 步骤 | 失败表现 |
|------|---------|
| `make_encode_device(disp, encoder, config)` | 编解码设备无法创建 |
| `make_encode_session(...)` | 编码会话无法创建 |
| `disp->alloc_img()` → `dummy_img()` → `session->convert()` | 图像分配/填充/转换失败 |
| `session->request_idr_frame()` 后循环 `encode(1, …)` 直到队列非空 | 编码直接报错 |
| 首个包必须是 IDR | 日志 `First packet type is not an IDR frame` |
| H.264/HEVC 时校验 SPS VUI（`cbs::validate_sps`） | 返回标志位不含 `VUI_PARAMS` |

返回值是一个位标志集合（目前只有 `VUI_PARAMS = 0x01`）；非 avcodec 编码器（如 NVENC 直连）跳过 VUI 检查，直接视为通过。

## 2. 视频采集管线

### 2.1 两种采集线程模型：`PARALLEL_ENCODING` 决定

`video::capture()`（[video.cpp:2986](../../../src/video.cpp#L2986)）是会话入口，第一件事就是把 IDR 事件置位（保证客户端拿到关键帧），然后**按编码器能力标志选择模型**：

```cpp
config = resolve_dynamic_range(*chosen_encoder, config);   // 先按编码器能力修正 HDR
idr_events->raise(true);
if (chosen_encoder->flags & PARALLEL_ENCODING) {
  capture_async(mail, config, channel_data);   // 采集与编码分离
} else {
  capture_thread_sync...                        // 采集与编码同线程、多会话复用
}
```

| 模型 | 触发条件 | 线程 | 特点 |
|------|---------|------|------|
| **async** | 编码器带 `PARALLEL_ENCODING` | `video::capture` + `video::encode`（每会话一个） | 采集一次可喂多个会话的编码器；延迟最低 |
| **sync** | 其它编码器 | 单个 `video::capture_sync` 承担全部会话的采集+编码 | 采集帧被多个会话共享，避免重复采集；编码串行 |

两个共享对象都是**引用计数惰性创建**（[video.cpp:709](../../../src/video.cpp#L709)）：

```cpp
auto capture_thread_async = safe::make_shared<capture_thread_async_ctx_t>(start_capture_async, end_capture_async);
auto capture_thread_sync  = safe::make_shared<capture_thread_sync_ctx_t >(start_capture_sync,  end_capture_sync );
```

即：**第一个会话启动时创建采集线程，最后一个会话退出时销毁**（`safe::make_shared` 的 `ref()` 计数归零即触发 stop 回调）。

### 2.2 `captureThread()`：L4 采集驱动的核心（[video.cpp:1580](../../../src/video.cpp#L1580)）

线程名 `video::capture`，线程优先级 **critical**。

**图像池**：固定 12 个槽位（`capture_buffer_size = 12`）的 `std::list<std::shared_ptr<platf::img_t>>`。

- `pull_free_image_callback`：优先复用 `use_count() == 1` 的已分配图像并把命中的槽位提到链表头（提高复用概率）；没有可复用的就 `alloc_img()` 分配新的；池满则 `sleep 1ms` 重试。
- `trim_imgs`：统计当前 `use_count() > 1`（正在被编码器使用）的数量作为下限，**超过 3 秒**未被使用的已分配图像会被释放；时间戳记录保留下来以免抖动。
- 每次交付前 `img_out->frame_timestamp.reset()`。

**推帧回调** `push_captured_image_callback`：把同一张图像 `raise` 给**所有**仍然 running 的 `capture_ctxs`（每个会话一个 `images` 事件槽）。

**显示切换**：`mail::switch_display`（[globals.h](../../../src/globals.h)）被 raise 时置 `artificial_reinit = true`，把本次 `capture()` 结果改成 `reinit`，从而走下面的重建流程。触发源是输入侧快捷键 **Ctrl+Alt+Shift+F1..F13**（[input.cpp:429](../../../src/input.cpp#L429) 起，`keyCode - VK_F1` 即显示器索引）。

**reinit 流程**（`platf::capture_e::reinit` 分支，[video.cpp:1763](../../../src/video.cpp#L1763)）：

```
reinit_event.raise(true)          ← 通知编码线程暂停并准备重建
  │
  ├─ 释放本线程持有的所有 img（img 可能反向引用 display）
  ├─ 自旋等待 display_wp 的 use_count 降到 1（其它线程已放开 display）
  │    期间持续排空未被消费的 images 队列
  │
  ├─ disp.reset()                  ← 某些采集后端每设备只允许一个会话，必须先释放
  ├─ refresh_displays(...)         ← 显示器可能被拔掉/插上，重新枚举
  ├─ 若有待处理的 switch_display → display_p = clamp(值, 0, n-1)
  ├─ reset_display(...)            ← 内部带重试 sleep
  ├─ display_wp = disp
  └─ reinit_event.reset() → continue（下一轮重新采集）
```

### 2.3 `capture_async()`：会话侧驱动循环（[video.cpp:2895](../../../src/video.cpp#L2895)）

```
1. images = make_shared<img_event_t::element_type>()       // 本会话的图像单槽
2. ref = capture_thread_async.ref()                        // 首个会话会在这里创建线程
3. ref->capture_ctx_queue->raise({images, config})          // 向采集线程注册本会话
4. 循环 while (!shutdown_event->peek() && images->running()):
     ├─ ref->reinit_event.peek()  → sleep 20ms, continue   // 显示重建期间空转
     ├─ 从 display_wp 弱引用取 display，过期则 continue
     ├─ encode_device = make_encode_device(*display, encoder, config)
     │    失败 → return（会话终止推流）
     ├─ touch_port_event->raise(make_port(display, config))  // 上报分辨率/缩放给输入系统
     ├─ hdr_event->raise(hdr_info)                          // 上报当前 HDR 状态与元数据
     └─ encode_run(frame_nr, mail, images, config, display,
                   std::move(encode_device), ref->reinit_event,

```

`make_port()`（[video.cpp:2535](../../../src/video.cpp#L2535)）把显示分辨率与客户端请求分辨率算出缩放因子，并叠加 KMS 的 `logical_width/height` 与 `env_logical_width/height`，产出 `input::touch_port_t`。这是**绝对坐标输入（鼠标/触摸/笔）能在正确位置上落点**的前提。

HDR 上报逻辑：编码设备 colorspace 是 HDR 时调用 `display->get_hdr_metadata()`；拿不到元数据会打 `Couldn't get display hdr metadata when colorspace selection indicates it should have one`。

### 2.4 `encode_run()`：编码主循环（[video.cpp:2420](../../../src/video.cpp#L2420)）

**① 会话创建 + 异步销毁兜底**

```cpp
auto fail_guard = util::fail_guard([&encoder, &session] {
  if (encoder.flags & ASYNC_TEARDOWN) {
    std::jthread t {[session = std::move(session)]() mutable {
      BOOST_LOG(info) << "Starting async encoder teardown";
      session.reset();
      BOOST_LOG(info) << "Async encoder teardown complete";
    }};
    t.detach();
  }
});
```

原因写在注释里：**NVENC 驱动偶发挂死**，把昂贵的销毁挪到独立线程，使编码线程能尽快重启；挂死场景下这个线程可能永不退出，但不会阻塞整个串流。带 `ASYNC_TEARDOWN` 的主要是 NVENC / VideoToolbox。

**② 帧率下限**

```cpp
minimum_fps_target = config::video.minimum_fps_target > 0 ? it : config.framerate / 2;
max_frametime = 1000.0 / minimum_fps_target;   // ms
```

即使画面静止（采集端不产帧），也会以 `max_frametime` 为超时上限，让循环继续跑——这是**避免静态画面下延迟累积、同时保持「活着」**的关键。

**③ 首帧占位**

进入循环前先 `alloc_img()` + `dummy_img()` + `convert()`，向编码器塞一张占位图。作用是：**即使第一帧采集超时，也能立刻产出一个包让客户端知道主机已就绪**。

**④ 循环体**

```
while (true) {
  requested_idr_frame = false;

  while (invalidate_ref_frames_events->peek())          // 参考帧失效（RFI）
    session->invalidate_ref_frames(first, last);

  if (idr_events->peek()) { requested_idr_frame = true; idr_events->pop(); }
  if (requested_idr_frame) session->request_idr_frame();

  optional<time_point> frame_timestamp;
  if (!requested_idr_frame || images->peek()) {          // 纯 IDR 请求且无新帧时不做无谓等待
    if (auto img = images->pop(max_frametime)) {
      frame_timestamp = img->frame_timestamp;
      if (session->convert(*img)) { /* "Could not convert image" */ return; }
    } else if (!images->running()) break;
  }

  if (shutdown_event->peek() || !images->running()
      || (reinit_event.peek() && frame_nr > 1)) break;   // 见下

  if (encode(frame_nr++, *session, packets, channel_data, frame_timestamp)) {
    /* "Could not encode video packet" */ return;
  }
  session->request_normal_frame();
  platf::enable_mouse_keys();                            // KVM 场景：让光标重新出现
}
```

**跳出条件**（必须在 encode 之前「尽可能接近」地判断，防止编码器销毁后仍有在途包）：

| 条件 | 含义 |
|------|------|
| `shutdown_event->peek()` | 会话结束 / Sunshine 退出 |
| `!images->running()` | 会话侧已停止推流 |
| `reinit_event.peek() && frame_nr > 1` | 采集侧重启中，且已编过至少一帧（`frame_nr == 1` 时故意放行，让占位帧先出） |

**⑤ 单槽事件的隐式丢帧**

`images` 的类型是 `img_event_t = shared_ptr<safe::event_t<shared_ptr<platf::img_t>>>`（[video.h:120](../../../src/video.h#L120)），而 `safe::event_t`（[thread_safe.h:24](../../../src/thread_safe.h#L24)）**只持有 1 个值**：

```cpp
template<class... Args> void raise(Args &&...args) { ... _status = make_optional<T>(...); ... }
```

因此 `push_captured_image_callback` 连续 raise 两帧而编码线程尚未 pop 时，**前一帧直接被覆盖丢弃**。这是整条视频链路里**真正意义上、也是唯一一处「设计上的显式丢帧」**：它保证了编码器永远拿到最新帧，不会在队列里积压陈旧画面。

> 与之对比，`mail::video_packets` 是容量 32 的 `queue_t`，其溢出策略 `drop_oldest` 在**满时会 `clear()` 整个队列**（见 [05 篇 §5](./05-FEC-重传-丢帧与心跳.md)）。两者一个在入口处丢、一个在出口处丢。

**优先级（[audio.cpp:189](../../../src/audio.cpp#L189) 注释原文）**：

```
1. 虚拟 sink   2. 配置的 sink   3. host
```

判定细节：

- 起点是 host sink；`config::audio.sink` 非空则改用配置值。
- 若存在虚拟 sink **且**（未启用 `HOST_AUDIO` **或** 用户没配 sink），则按声道数选用虚拟 sink 的 `stereo` / `surround51` / `surround71`。
- **只允许第一个启动的会话切换默认 sink**：`ref->sink_flag->exchange(true)` 首次返回 `false` 时执行切换；`restore_sink = (现有 sink != 目标 sink)`，为真则 `control->set_sink(sink)`。
- `stop_audio_control` 时若 `restore_sink` 为真则恢复原 sink。

`platf::audio_control_t` 接口（[platform/common.h:819](../../../src/platform/common.h#L819)）：

| 方法 | 作用 |
|------|------|
| `set_sink(sink)` | 切换系统默认输出设备（Windows 下含虚拟声卡） |
| `microphone(mapping, channels, sample_rate, frame_size, continuous, host_audio_enabled)` | 建立采集流，返回 `mic_t` |
| `is_sink_available(sink)` | 检查 sink 是否存在（WebUI 用它做可用性校验） |
| `sink_info()` | 返回 host / 虚拟 sink 名 |

## 4. 重配与重建的触发点

| 触发源 | 机制 | 落到哪里 |
|--------|------|---------|
| 显示器热插拔 / 分辨率变化 | L4 `capture()` 返回 `platf::capture_e::reinit` | 采集线程重建 display，`reinit_event` 通知编码线程跳出并重建会话 |
| 用户快捷键 **Ctrl+Alt+Shift+F1..F13** | [input.cpp:429](../../../src/input.cpp#L429) → `mail::switch_display` | 采集线程置 `artificial_reinit`，下一轮按新索引重建 display |
| 客户端请求 IDR | 控制通道 `IDX_REQUEST_IDR_FRAME` → `video::idr_events` | `encode_run` 循环顶部 `session->request_idr_frame()` |
| 客户端 RFI | 控制通道 `IDX_INVALIDATE_REF_FRAMES` → `video::invalidate_ref_frames_events` | `session->invalidate_ref_frames(first, last)` |
| 会话结束 | `mail::shutdown` | `encode_run` 跳出 → `ASYNC_TEARDOWN` 在独立线程销毁编码器 |
| 编码器选择变化 | `platf::needs_encoder_reenumeration()` / `ALWAYS_REPROBE` | 下次 `probe_encoders()` 重新探测（不再复用缓存） |

> **注意**：编码器**不会**因为码率/分辨率变化自动重建。码率是客户端在 `cmd_announce` 时一次性协商的，运行中调整码率需要客户端重新发起会话（详见 [04 篇](./04-码率控制与QoS.md)）。

## 6. 小结

1. **编码器是「先探测、后复用」的静态清单**：`probe_encoders()` 按编译期顺序逐个真跑一帧，结果被缓存供后续所有会话复用，只有 `ALWAYS_REPROBE` 或平台要求重枚举时才重来。
2. **采集与编码有两种线程模型**，由编码器的 `PARALLEL_ENCODING` 决定；两者都通过「采集线程引用计数惰性创建、最后一个会话退出时销毁」的方式共享。
3. **`images` 是单槽事件**，这是整条视频链路上唯一一处设计上的显式丢帧点——它的目的就是让编码器永远只面对「最新的一帧」。
4. **音频与视频的容错姿态不同**：视频失败会终止推流（`return`），音频失败只让音频线程挂起并打出 `The stream will not have audio.`，画面继续。
5. **`reinit_event` 是显示层与编码层之间的唯一同步信号**，所有显示重建（热插拔、分辨率变化、快捷键切屏）都汇聚到它。
