### 1.1 nvhttp —— GameStream 发布器（`src/nvhttp.cpp`）

### 1.3 rtsp_stream —— 会话建立（`src/rtsp.cpp`）

端口 `net::map_port(RTSP_SETUP_PORT)`，`RTSP_SETUP_PORT = 21`（默认 48010）。

**方法映射**（`src/rtsp.cpp:1338` 起）

| RTSP 方法 | 处理函数 | 作用 |
|-----------|---------|------|
| `OPTIONS` | `cmd_option` | 能力探测 |

## 2. 配对与三条信任链

### 2.1 配对（`/pair`）

```
客户端                                    服务端 (nvhttp)
  │  GET  /pair   (无证书)                   │
  │─────────────────────────────────────────►│ 阶段1: 返回服务端证书 (salt/随机挑战)
  │◄─────────────────────────────────────────│
  │  POST /pair  (client cert + AES(挑战))    │
  │─────────────────────────────────────────►│ 阶段2~4: 校验，得到 AES key
  │◄─────────────────────────────────────────│
  │  POST /pair  (验证用 AES(挑战))           │
  │─────────────────────────────────────────►│ 阶段5: 校验通过
  │◄─────────────────────────────────────────│ 落盘 named_cert + 生成随机 PIN → 显示在 WebUI
```

- 配对会话放在 `std::unordered_map<std::string, pair_session_t> map_id_sess`，key 是 16 位十六进制临时 ID（`crypto::rand_alphabet(PAIRING_ID_SIZE, "0123456789abcdef")`）。
- 有 PIN 超时清理：`expire_pair_sessions_unlocked(now)`。
- PIN 校验用 `is_valid_pairing_id` / `is_valid_pairing_pin` / `is_valid_pairing_name`。
- 配对结果落到 `client_root.named_devices`，即「已配对客户端数据库」。

### 2.2 三条信任链

| 链路 | 传输 | 密钥来源 | 算法 | 是否强制 |
|------|------|---------|------|---------|
| **① GameStream HTTPS** | TCP/TLS | X.509 客户端证书（配对时交换） | TLS + 证书指纹白名单 | 配对必须 |
| **② RTSP** | TCP | `rikey`（`/launch` 时随机生成，随响应下发） | AES-128-GCM；`rtsp_iv_counter` 递增 | 由加密策略决定 |
| **③ 控制通道** | UDP/ENet | 从 `rikey`+`gcm_key` 派生 | AES-128-GCM（控制协议 13，或 legacy IV 模式） | 由加密策略决定 |
| **④ 视频流** | UDP | 同上 | AES-128-GCM（IV = 递增计数器 ‖ `'V'`） | 由加密策略决定 |
| **⑤ 音频流** | UDP | `avRiKeyId`（`launch_session.iv` 前 4 字节，大端） | AES-128-CBC（PKCS7 填充到 16 字节对齐） | **始终开启** |

**加密策略来源于配置 + 对端地址**：

```cpp
// src/network.cpp: encryption_mode_for_address(address)
// 依据地址是否属于 LAN 网段，返回 wan_encryption_mode 或 lan_encryption_mode
//   ENCRYPTION_MODE_NEVER      = 0  从不加密
//   ENCRYPTION_MODE_OPPORTUNISTIC = 1  客户端支持才加密
//   ENCRYPTION_MODE_MANDATORY  = 2  必须加密，否则 403
```

`cmd_announce` 里会检查：

```cpp
if (encryption_mode == ENCRYPTION_MODE_MANDATORY &&
    (config.encryptionFlagsEnabled & (SS_ENC_VIDEO | SS_ENC_AUDIO)) != (SS_ENC_VIDEO | SS_ENC_AUDIO)) {
  BOOST_LOG(error) << "Rejecting client that cannot comply with mandatory encryption requirement";
  respond(sock, session, &option, 403, "Forbidden", req->sequenceNumber, {});
}
```

**密钥材料生成点**（`src/nvhttp.cpp:469` `make_launch_session`）：

| 字段 | 生成方式 | 用途 |
|------|---------|------|
| `gcm_key` | `rikey`（`/launch` 时随机） | RTSP/控制/视频的 AES-GCM 密钥 |
| `av_ping_payload` | `RAND_bytes(raw_payload, 8)` → `util::hex_vec`（16 个 hex 字符） | UDP 通道「认领会话」的标识 |
| `control_connect_data` | `RAND_bytes(u32)` | 控制通道会话配对 |
| `iv` | 16 字节随机前缀 IV | 音频 `avRiKeyId` 来源 |

`SETUP` 时下发（`src/rtsp.cpp:1053-1058`）：

```cpp
if (type == "control") {
  payload_option.option  = "X-SS-Connect-Data";
  payload_option.content = std::to_string(session.control_connect_data);
} else {  // video / audio
  payload_option.option  = "X-SS-Ping-Payload";
  payload_option.content = session.av_ping_payload.data();
}
```

**RTSP 会话超时**：`rtsp_server_t::session_raise`（`src/rtsp.cpp:595`）在 `raised_timer` 上启动 `config::stream.ping_timeout`；超时后弹出待处理 launch session 并记录 `"Event timeout: <unique_id>"`。

## 3. `stream::session` 与 `broadcast_ctx_t`

### 3.1 会话状态机

```cpp
// src/stream.h
enum class state_e { STOPPED, STOPPING, STARTING, RUNNING };
```

```
                   session::alloc()          session::start()
   STOPPED ─────────────────────────► STOPPED ──────────────► RUNNING
                                                               │
                        session::stop()  (CAS RUNNING→STOPPING)
                                                               ▼
                                                           STOPPING
                                                               │
                             control 线程检测到 STOPPING → 从 _sessions 移除
                             session::join() 等所有子线程退出
                                                               ▼
                                                           (销毁)
```

- `running_sessions` 是进程级原子计数器。
- `session::stop()` 先自旋等 `STARTING` 结束，再 CAS `RUNNING→STOPPING`（幂等），最后 `shutdown_event->raise(true)`。
- `session::join()` 会挂一个 10 秒看门狗：

```cpp
task_pool.pushDelayed([]() {
  BOOST_LOG(fatal) << "Hang detected! Session failed to terminate in 10 seconds.";
  lifetime::debug_trap();   // 故意崩溃，方便抓 dump（规避 NVENC 硬件调度死锁）
}, 10s);
```

### 3.3 `broadcast_ctx_t` 线程布局

```cpp
// src/stream.cpp:470 附近
struct broadcast_ctx_t {
  message_queue_queue_t message_queue_queue;        // 容量 30，UDP PING → session 路由表
  std::jthread recv_thread;                         // UDP 收包 + PING 匹配
  std::jthread video_thread;                        // 视频：等 PING → 设 QoS → capture
  std::jthread audio_thread;                        // 音频：同上
  std::jthread control_thread;                      // ENet 控制通道 + 超时/反馈
  boost::asio::io_context io_context;
  udp::socket video_sock, audio_sock;
  control_server_t control_server;
};

static auto broadcast = safe::make_shared<broadcast_ctx_t>(start_broadcast, end_broadcast);
```

- **懒创建**：`safe::make_shared` 在第一次 `broadcast.ref()` 时调 `start_broadcast`，引用计数归零时调 `end_broadcast`。
- `start_broadcast`（`src/stream.cpp:1958`）：
  1. `net::get_effective_address_family(...)` 决定地址族；
  2. `control_server.bind()` → `net::host_create(af, addr, net::map_port(CONTROL_PORT))`（ENet + 可靠 UDP）；
  3. 打开 `video_sock`，`send_buffer_size(1 MiB)`（失败只记日志）；
  4. 绑定 `video_sock` / `audio_sock` 到 `VIDEO_STREAM_PORT` / `AUDIO_STREAM_PORT`；
  5. 建 `message_queue_queue`（容量 30）；
  6. 拉起 4 个 `jthread`。
- `end_broadcast`（`src/stream.cpp:2028`）：`mail::broadcast_shutdown` → stop `video_packets`/`audio_packets` 队列 → stop `message_queue_queue` → `io_context.stop()` → 关两个 UDP socket → **按 recv → video → audio → control 的顺序 join**（避免 recv 还在往已停的队列里塞数据）→ `broadcast_shutdown_event->reset()`。

### 3.4 `control_server_t` 的会话配对（`src/stream.cpp:371`）

这是「UDP 控制包如何找到正确的 session」的核心：

```
control_server_t::get_session(peer, connect_data)
   │
   ├─ 快路径：_peer_to_session 里已有该 peer → 直接返回
   │
   └─ 慢路径：遍历 _sessions，找 control.peer == nullptr 的 session
         ├─ 若客户端声明支持 ML_FF_SESSION_ID_V1 → 比对 connect_data
         └─ 否则 → 比对 expected_peer_address（客户端 IP）
         │
         匹配成功：
           rtsp_stream::launch_session_clear(session->launch_session_id)  ← 让 RTSP 侧松手
           session->control.peer   = peer
           session->localAddress   = peer->localAddress
           _peer_to_session[peer]  = session
```

**安全门禁**：当 `controlProtocolType == 13`（加密控制协议）时，`control_server_t::call()` 拒绝任何未加密消息，除非：

- 该消息是「重新注入」的（`reinjected`，即外层 `IDX_ENCRYPTED` 解出来的内层消息），或
- 类型就是 `IDX_ENCRYPTED`。

未知类型会以 debug 级别 hex dump 出来。

**超时刷新**：`control_server_t::iterate(timeout)` → `enet_host_service()`，**任何**事件都会刷新：

```cpp
session->pingTimeout = std::chrono::steady_clock::now() + config::stream.ping_timeout;
```

未匹配到任何 session 的新连接：

```
BOOST_LOG(warning) << "Control: Received a connection from ... but it's not properly set up";
enet_peer_disconnect_now(event.peer, 0);
```

## 4. ★ 首次客户端连接 → 推流 → 断开（完整时序）

### 4.1 阶段总览

```
 阶段                    客户端                            服务端
 ════════════════════════════════════════════════════════════════════════
 ① 发现/鉴权     →  GET /serverinfo                      nvhttp 返回主机信息
                 →  GET /applist                          nvhttp 返回应用列表
 ② 启动请求      →  GET /launch?appid=…&rikey=…           nvhttp:
                     &rikeyid=…&localport=…                 · 校验客户端证书
                     &mode=…&hdrMode=…                      · make_launch_session()
                     &surroundAudioInfo=…                    ├ RAND rikey → gcm_key
                                                            ├ RAND 8B → av_ping_payload
                                                            ├ RAND u32 → control_connect_data
                                                            └ RAND 16B → iv
                                                          rtsp_stream::launch_session_raise(sess)
                                                          返回 XML: sessionUrl0 = rtsp://…:48010
 ③ RTSP 协商     →  OPTIONS   rtsp://…                    cmd_option  200
                 →  DESCRIBE  rtsp://…                    cmd_describe 200 (+认证)
                 →  ANNOUNCE  rtsp://…                    cmd_announce ★
                     (SDP: video/audio/control 三段)         解析 SDP → 决定
                                                             分辨率/帧率/码率/FEC/
                                                             加密标志/包大小/色度
                                                             stream::session::alloc()
                                                             stream::session::start()
                                                             → 200 OK
                 →  SETUP  streamid=video/audio/control    cmd_setup 200
                     ← X-SS-Ping-Payload (video/audio)
                     ← X-SS-Connect-Data (control)
                 →  PLAY                                   cmd_play 200 (只回 CSeq!)
 ④ UDP 握手      →  向 video 端口发 SS_PING{payload,seq}   recvThread: 按 payload 匹配
                 ← (无响应, 单向)                          videoThread: 记下真实客户端端口
                                                           platf::enable_socket_qos(...)
                 →  向 audio 端口发 SS_PING                audioThread: 同上
                 →  控制通道 ENet CONNECT (connect_data)    control_server: get_session()
                                                           session->control.peer = peer
 ⑤ 推流          ←  视频 UDP 流 (RTP+FEC+AES-GCM?)          video::capture → encode → FEC → 配速
                 ←  音频 UDP 流 (RTP+FEC+AES-CBC)          audio::capture → Opus → AES-CBC → 4+2 FEC
                 ←  控制通道 ENet (可靠)                   力反馈/HDR/终止原因
                 →  控制通道: 输入包 / 心跳 / LossStats      input::passthrough / pingTimeout 刷新
 ⑥ 断流          →  ENet DISCONNECT / RTSP TEARDOWN        control 线程: session::stop()
                 →  GET /cancel (超时兜底)                  session::join()
                                                           input::reset(input)
                                                           --running_sessions == 0 时:
                                                             · display_device 配置还原
                                                             · input::terminate_gamepads()
                                                             · platf::streaming_will_stop()
```

### 4.2 分平面泳道时序（带源码位置）

一次完整会话跨 **TCP 控制面** 与 **UDP 数据面** 两个平面。下面按平面分别画泳道：`│` 是时间轴，箭头方向即消息方向，行尾的 `文件:行` 是与该步强相关的源码位置。

#### 4.2.1 平面 A —— TCP：发现 → 启动 → RTSP 协商

```

   │                           │                                    │
 1 │ GET /serverinfo ─────────►│ serverinfo<>()      nvhttp.cpp:1207
   │◄─── 200 XML（主机名 / 端口表 / 配对状态 / 版本）
   │                           │
 2 │ GET /applist ────────────►│ applist             nvhttp.cpp:1296
   │◄─── 200 XML（应用列表，含 appid）
   │                           │

   │                           ├ 校验客户端证书链 → last_verified_client_cert   nvhttp.cpp:1669
   │                           ├ make_launch_session()                           nvhttp.cpp:469
   │                           │    ├ RAND 16B → rikey（= gcm_key）
   │                           │    ├ RAND 16B → iv
   │                           │    ├ RAND u32 → control_connect_data
   │                           │    └ RAND  8B → av_ping_payload（转 16 位 hex）
   │                           ├ if (session_count() == 0) {
   │                           │     display_device::configure_display(...)   ← 改分辨率/刷新率
```

### 4.6 阶段 ④ 细节：UDP PING 握手（`recv_ping`）

`recv_ping(session, ref, socket_e, expected_payload, peer, timeout)`（`src/stream.cpp:2073`）是**推流真正的起点**：

```
recv_ping(...)
   ├─ 在 message_queue_queue 里注册一个 30 元素队列，key 为：
   │     · std::string{expected_payload}                     （v2 客户端）
   │     · 以及 peer.address()（仅当客户端不支持 ML_FF_SESSION_ID_V1 的旧客户端）
   ├─ 循环等待（上限 config::stream.ping_timeout）
   │     收到含 expected_payload 的包 → v2 成功
   │     收到内容恰为 "PING" 的 4 字节包 → v1（legacy）成功
   │        └ 成功后 peer = recv_peer（记录客户端真实端口）
   │     timeout → "Initial Ping Timeout" → 返回 -1
   └─ 无论成功失败，fail_guard 都注销两个 key 并 stop 该队列
```

**两种 PING 的判据**（`recvThread`，`src/stream.cpp:1423`）：

| 收到的字节数 | 判据 | 匹配依据 |
|:-----------:|------|---------|
| `== 4` | 内容是 `"PING"` | **peer 地址**（无法携带 payload） |
| `>= sizeof(SS_PING)` (=20) | `SS_PING.payload[16]` 字符串 | **payload 字符串** |

```cpp
// third-party/moonlight-common-c/src/Video.h:51
typedef struct _SS_PING {
  char payload[16];
  uint32_t sequenceNumber;
} SS_PING;
```

`recvThread` 维护两张路由表 `peer_to_video_session` / `peer_to_audio_session`，key 是 `av_session_id_t`：

```cpp
recvThread:
  while (!mail::broadcast_shutdown) {
    populate_peer_to_session();        // 每次收包前把 message_queue_queue 里的条目刷进路由表
                                       //   队列为空(nullptr) → 从路由表删除
    异步 recv video_sock / audio_sock  (2048 字节缓冲)
    匹配成功 → queue->raise(peer, msg)

```

### 4.8 阶段 ⑥：断开与收尾（总览）

断开的**唯一收敛点**是 `stream::session::stop()`（`src/stream.cpp:2200`）：它把 `state` 从 `RUNNING` 原子地置为 `STOPPING` 并 `raise(shutdown_event)`，其余所有线程都只是"看到 STOPPING 后各自退出"。**全部 8 条触发路径**及其精确入口见 [§5 断开路径全集](#5-断开路径全集)。

| 触发 | 入口 | 处理 |
|------|------|------|
| 客户端主动断开 ENet | `control_server_t::iterate` 收到 `ENET_EVENT_TYPE_DISCONNECT` | 若 `state == RUNNING` → `session::stop` |
| 控制通道心跳超时 | `controlBroadcastThread` 每轮检查 `now > session->pingTimeout` | 记 `"Ping Timeout"` → `session::stop` |
| 控制通道解密/校验失败 | `IDX_ENCRYPTED` 分支 GCM tag 失败或内层又是 `IDX_ENCRYPTED` | `session::stop` |
| 应用退出 / 进程结束 | `controlBroadcastThread` 主循环条件 `proc::proc.running() == 0 && !has_session_awaiting_peer` 不再成立 | 退出循环 → 广播 `IDX_TERMINATION` |
| RTSP 侧 `/cancel` | `nvhttp::cancel` → `rtsp::terminate_sessions()` | `server.clear(true)` + `input::terminate_gamepads()` |
| 解除配对 / 证书撤销 | `confighttp` 解除配对 → `rtsp::terminate_sessions_by_cert(cert)` | `server.clear_by_cert(cert)` + `input::terminate_gamepads(cert)` |
| 全局关闭（SIGINT / 托盘退出） | `mail::shutdown` 事件 | 各广播线程退出；RTSP 线程 `server.clear()` |
| UDP PING 从未到达 | `recv_ping()` 超时返回 -1 | `videoThread`/`audioThread` 的 `fail_guard` → `session::stop` |

**`controlBroadcastThread` 的收尾逻辑**（`src/stream.cpp:1164`）：

```cpp

```

## 5. 断开路径全集

### 5.1 唯一收敛点：`session::stop()`

```cpp
// src/stream.cpp:2200
void stop(session_t &session) {
  while_starting_do_nothing(session.state);      // 若仍在 STARTING 则自旋等待
  auto expected = state_e::RUNNING;
  auto already_stopping = !session.state.compare_exchange_strong(expected, state_e::STOPPING);
  if (already_stopping) {
    return;                                     // 幂等：谁先到谁负责，后到者直接返回
  }
  session.shutdown_event->raise(true);          // 唤醒所有在等 shutdown 的线程
}
```

两个关键性质：

- **不做任何 join**，所以可以从任意线程、任意时刻安全调用（包括 `controlBroadcastThread` 自己的循环里）。
- `compare_exchange_strong` 保证在多条路径同时触发时只有一次"真正生效"，其余全部走 `return`。

### 5.2 八条路径一张表

| **P4** | UDP PING 从未到达 | 服务端看门狗 | `recv_ping()` 超时 → `videoThread`/`audioThread` 的 `fail_guard` → [stream.cpp:2131](../../../src/stream.cpp#L2131) | 静默 | RTSP 成功了但一直黑屏后掉线 |
| **P5** | 应用退出 / 主机侧结束 | 主机 | `controlBroadcastThread` 主循环退出 → 广播 `IDX_TERMINATION`（`0x80030023`） → [stream.cpp:1377](../../../src/stream.cpp#L1377) | **优雅** | 收到"主机已结束串流"提示 |
| **P6** | 客户端点"退出游戏" | 客户端 HTTP | `nvhttp::cancel` [nvhttp.cpp:1546](../../../src/nvhttp.cpp#L1546) → `rtsp_stream::terminate_sessions()` [nvhttp.cpp:1561](../../../src/nvhttp.cpp#L1561) | 强制 | 自己发起的 |
| **P7** | 解除配对 / 证书撤销 | WebUI | `rtsp_stream::terminate_sessions_by_cert(cert)` → [confighttp.cpp:1317](../../../src/confighttp.cpp#L1317) | 强制 | 下一帧就断 |
| **P8** | Sunshine 进程退出 | OS / 托盘 | `mail::shutdown` 事件 → 各线程退出 → `rtsp_server_t::stop()` [rtsp.cpp:722](../../../src/rtsp.cpp#L722) | 尽力优雅 | 可能来不及收到终止包 |

`/cancel` 的完整动作（[nvhttp.cpp:1546](../../../src/nvhttp.cpp#L1546)）：

```cpp
// src/nvhttp.cpp:1561
rtsp_stream::terminate_sessions();        // server.clear(true)：stop + join + erase（同步阻塞！）
if (proc::proc.running() > 0) {
  proc::proc.terminate();                 // nvhttp.cpp:1564 顺手把主机侧的游戏进程也结束掉
}
display_device::revert_configuration();   // nvhttp.cpp:1568 无论是否杀了进程都要还原显示配置
```

> 注意 `/cancel` 走的是**强制**路径：`clear(true)` 会对**所有**会话（不只是当前客户端）执行 `stop` + `join`。

### 5.4 P5 细节：为什么"优雅终止"由应用退出触发

```cpp
// controlBroadcastThread 主循环，src/stream.cpp:1313
while (!shutdown_event->peek() && !broadcast_shutdown_event->peek()) {
  /* 遍历 _sessions：超时 stop / STOPPING 收尸 / 排空力反馈与 HDR 队列 */
  if (proc::proc.running() == 0 && !has_session_awaiting_peer) {
    BOOST_LOG(info) << "Process terminated";
    break;
  }
  server->iterate(150ms);
}

// 退出前，向所有仍有 ENet peer 的会话发送终止原因
std::uint32_t reason = 0x80030023;              // graceful termination
control_terminate_t plaintext;
plaintext.header.type = packetTypes[IDX_TERMINATION];
plaintext.ec = util::endian::big<uint32_t>(reason);
/* 逐会话 encode_control → send → shutdown_event->raise(true) → controlEnd.raise(true) */
server->flush();
```

- `proc::proc.running() == 0` 意味着**主机侧的游戏进程消失了**（用户自己在主机上退出、游戏崩溃等）。这是唯一会主动告知客户端"原因"的路径。
- `has_session_awaiting_peer` 是为了消掉一个竞态：应用在客户端还没连上控制通道时就退了，此时仍要多等一会儿，把终止包发得出去。
- `0x80030023` 就是 Moonlight 侧显示"主机已结束串流"的原因码。

### 5.5 P6 / P7 细节：三种清理函数的差别

| | `server.clear(true)` | `server.clear(false)` | `server.clear_by_cert(cert)` |
|---|---|---|---|
| 定义位置 | [rtsp.cpp:652](../../../src/rtsp.cpp#L652) | 同左 | [rtsp.cpp:673](../../../src/rtsp.cpp#L673) |
| 选中条件 | 全部会话 | 仅 `state == STOPPING` | 仅 `client_cert == cert` |
| 动作 | `stop` + `join` + `erase` | 同左 | 同左 |
| 由谁调用 | `terminate_sessions()`、`rtsp_server_t::stop()`、广播关闭时 | 每轮 `iterate`（例行收尸） | `terminate_sessions_by_cert()` |
| 阻塞性 | **同步阻塞**到线程全部退出 | 同左 | 同左 |

外层包装：

| 函数 | 定义 | 组合动作 | 调用方 |
|------|------|---------|--------|
| `rtsp_stream::terminate_sessions()` | [rtsp.cpp:760](../../../src/rtsp.cpp#L760) | `server.clear(true)` + `input::terminate_gamepads()`（全部） | `nvhttp::cancel` |
| `rtsp_stream::terminate_sessions_by_cert(cert)` | [rtsp.cpp:768](../../../src/rtsp.cpp#L768) | `server.clear_by_cert(cert)` + `input::terminate_gamepads(cert)`（仅该客户端） | `confighttp` 解除配对 |

> 所以 `/cancel` 的 HTTP 响应会被"等 4 个广播线程退出"拖住。这也是 `rtsp_server_t::iterate()` 在 `session_count() > 0` 时使用 `io_context.run_one_for(500ms)` 而非 `run_one()` 的原因——保证清理能周期性推进（[rtsp.cpp:709](../../../src/rtsp.cpp#L709)）。

### 5.6 P2 细节：`pingTimeout` 由谁刷新、谁检查

```
   任何 ENet 事件（RECEIVE / CONNECT / DISCONNECT）
        └─ control_server_t::iterate           stream.cpp:763
              session->pingTimeout = steady_clock::now() + config::stream.ping_timeout;

   到期检查（主循环每轮 ≈150ms，server->iterate(150ms)）
        └─ controlBroadcastThread              stream.cpp:1329
              if (now > session->pingTimeout) { log "Ping Timeout"; session::stop(); }
```

- `ping_timeout` 默认 **10 s**（`src/config.cpp:1811`）。
- 客户端按周期发的 `IDX_PERIODIC_PING`（`0x0200`）只是充当"心跳负载"，服务端**完全不解析其内容**——任何 ENet 事件都算"活着"。
- **与 UDP 平面无关**：UDP 侧的 `SS_PING` 只在会话建立时用一次（`recv_ping`）。所以"控制通道活着但 UDP 断了"不会导致会话结束——视频靠 FEC + 客户端 RFI 自愈（见 [05 篇](./05-FEC-重传-丢帧与心跳.md)）。这正是"心跳放在控制通道而不是流通道"的设计收益。

### 5.7 谁在等谁：阻塞点与兜底一览

| 等待方 | 被等待方 | 唤醒 / 超时兜底 |
|--------|---------|----------------|
| `session::stop()` | `STARTING` 阶段结束 | 自旋 `while_starting_do_nothing` |
| `session::join()` | `videoThread`、`audioThread` | **10 s 看门狗** → `"Hang detected! Session failed to terminate in 10 seconds."` + `lifetime::debug_trap()` |
| `session::join()` | `controlEnd` 事件 | 由 `controlBroadcastThread` 收尸时 `controlEnd.raise(true)` |
| `rtsp_server_t::clear()` 的调用者 | 上面的 `join()` | 无自身超时（依赖 join 的看门狗） |
| `end_broadcast()` | 4 个广播线程 | 无超时（它们都被已 raise 的事件唤醒） |
| `recv_ping()` | 客户端首个 UDP PING | `config::stream.ping_timeout`；失败 `"Initial Ping Timeout"` 并返回 -1 |
| RTSP pending 槽 | 客户端发起 RTSP 连接 | `raised_timer` = `ping_timeout`（[rtsp.cpp:595](../../../src/rtsp.cpp#L595)）→ 日志 `"Event timeout: <unique_id>"` |

**为什么 10 s 看门狗要"故意崩溃"**：NVENC 在启用硬件加速 GPU 调度时可能死锁编码线程，届时 Sunshine 会永久无法再开会话；主动 `debug_trap()` 让服务重启是唯一能自愈的选择。

## 6. 控制通道消息分发（`controlBroadcastThread` 的处理表）

| 消息 | 处理 |
|------|------|
| `IDX_PERIODIC_PING` (0x0200) | 仅记录（`pingTimeout` 已由 `iterate` 刷新） |
| `IDX_START_A` (0x0305) / `IDX_START_B` (0x0307) | 仅记录（日志用途） |
| `IDX_LOSS_STATS` (0x0201) | 解析 `int32_t[4]`（包数, 毫秒, ?, 最后成功帧号）→ **仅记录，不做任何自适应** |
| `IDX_REQUEST_IDR_FRAME` (0x0302) | `session->video.idr_events->raise(true)` |
| `IDX_INVALIDATE_REF_FRAMES` (0x0301) | `session->video.invalidate_ref_frames_events->raise({firstFrame, lastFrame})` |
| `IDX_INPUT_DATA` (0x0206) | 旧协议（未加密）：BE int32 长度前缀 → AES-GCM（`legacy_input_enc_iv`，IV 链式：拷贝上一个 IV 的后 16 字节）→ `input::passthrough` |
| `IDX_ENCRYPTED` (0x0001) | 解 `control_encrypted_t` → 按内层类型重新分发（`reinjected = true`）；GCM tag 校验失败 → `session::stop` |

**`IDX_ENCRYPTED` 的两种 IV 方案**：

| 方案 | 条件 | IV 构造 |
|------|------|---------|
| 新（V2） | `SS_ENC_CONTROL_V2` | 12 字节 `seq` ‖ `'C'` ‖ `'C'` |
| 旧（legacy） | 其他 | 16 字节 IV，`iv[0] = seq` |

**发送侧**（`encode_control<max_payload_size>`，`src/stream.cpp:570`）：

```cpp
if (controlProtocolType != 13) → 明文发送
else {
  seq = session->control.seq++;

    encryptedHeaderType = LE(0x0001),

```

## 7. 小结

| 关注点 | 结论 |
|--------|------|
| 谁决定编码参数 | **客户端**（RTSP ANNOUNCE 里的 SDP），服务端只做校验/夹取/回算 |
| 推流何时开始 | **UDP PING 到达**时，不是 `PLAY` 时 |
| 会话如何配对 | 控制通道用 `connect_data` 或客户端 IP；视频/音频用 `av_ping_payload` |
| 三条独立心跳 | ENet 事件刷新 `pingTimeout`；UDP 首次 PING 带 `ping_timeout`；RTSP `raised_timer` 同值 |
| 断流后谁来清理 | `control` 线程收尸 → `session::join` 做线程 join + 输入/显示/设备还原 |
