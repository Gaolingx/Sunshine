## 1. 日志系统速览

### 1.1 日志文件在哪

`config::sunshine.log_file` 的默认值是 `platf::appdata() + "/sunshine.log"`（[src/config.cpp:906](../../../src/config.cpp#L906)），而 `platf::appdata()` 各平台定义如下：

| 平台 | `platf::appdata()` | 日志的典型完整路径 |
|------|--------------------|-------------------|
| Windows | `sunshine.exe` 同级的 `config\` 目录（[src/platform/windows/misc.cpp:147](../../../src/platform/windows/misc.cpp#L147)） | `C:\Program Files\Sunshine\config\sunshine.log` |
| Linux | `$CONFIGURATION_DIRECTORY/sunshine` → `$XDG_CONFIG_HOME/sunshine` → `~/.config/sunshine`（[src/platform/linux/misc.cpp:279](../../../src/platform/linux/misc.cpp#L279)） | `~/.config/sunshine/sunshine.log` |
| macOS | `~/.config/sunshine`（[src/platform/macos/misc.mm:105](../../../src/platform/macos/misc.mm#L105)） | `~/.config/sunshine/sunshine.log` |

可用配置项 `log_path` 改到别处（[src/config.cpp:1768](../../../src/config.cpp#L1768)）。

★ **先记住这个结论**：`sunshine.log` 就躺在 `sunshine.conf`、`sunshine_state.json`、`apps.json`、`credentials/` 旁边。所以"把整个 `config` 目录打包带走"就等于把排障所需的全部现场材料带上了。

这个目录里每个文件都对应第 9 章的一条回滚路径，先一次性列清：

| 文件 / 目录 | 由谁读写 | 删掉或改坏会怎样 | 回滚难度 |
|-------------|----------|------------------|----------|
| `sunshine.conf` | 用户手写，`config::parse()` 读 | 配置不生效或解析不到；非法项只报 warning 不会崩 | ★ 最容易 |
| `sunshine.log`(+`.1`…`.5`) | 日志系统 | 只丢历史，无功能影响 | — |
| `apps.json` | `config::stream.file_apps`，WebUI 应用页维护 | 应用列表变空；Sunshine 会用 `SUNSHINE_ASSETS_DIR/apps.json` 模板重建（[src/config.cpp:1824](../../../src/config.cpp#L1824)） | ★ 容易 |
| `sunshine_state.json` | `config::nvhttp.file_state`，配对状态 | 所有已配对设备失效 | ★★ 需重新配对 |
| `credentials/` | WebUI 账号密码与证书 | 打不开 WebUI（可用 `--creds` 重置，见 [docs/troubleshooting.md](../../../docs/troubleshooting.md)） | ★★ |
| `display_device.state` | `display_device::init()` 的崩溃恢复记录（[src/main.cpp:297](../../../src/main.cpp#L297)） | 分辨率 / 刷新率残留为推流时的值 | ★★★ 见 §9 R3，有专门 API |
| `covers/` | 应用封面图 | 图标缺失 | — |

### 1.2 每次启动都轮转，只保留 5 份历史

```
config/
  sunshine.log      ← 本次运行，正在写
  sunshine.log.1    ← 上一次运行
  sunshine.log.2    ← 上上次
  sunshine.log.3
  sunshine.log.4
  sunshine.log.5    ← 最早保留的一份，再旧就被删掉
```

轮转在 `logging::init()` 里完成（[src/logging.cpp:160](../../../src/logging.cpp#L160)），保留份数是编译期常量 `retained_log_file_count {5}`（[src/logging.h:43](../../../src/logging.h#L43)）：先把 `.5` 删掉，再把 `.4`→`.5`、`.3`→`.4` … `.log`→`.1` 依次改名。

⚠️ **WebUI 的日志页看的是"当前那一份"**。`GET /api/logs` 直接读 `config::sunshine.log_file`（[src/confighttp.cpp:1652](../../../src/confighttp.cpp#L1652)），**不读 `.1`~`.5`**。要看"上一次崩溃前的日志"，必须到文件系统里翻。

⚠️ 如果 `sunshine.log` 被占用或没权限改名，轮转会失败，而这条失败信息**只写到 `stderr`、不进日志文件**（因为本来就写不进去）：

```
Failed to rotate log file '<路径>': <系统错误>
```
（[src/logging.cpp:161](../../../src/logging.cpp#L161)）——Windows 服务模式下 stderr 无处可看。所以"日志文件永远是同一份旧的、或根本没生成"时，先怀疑权限/占用，而不是日志系统坏了。

### 1.3 一行日志由三段构成

格式由自定义 formatter 决定（[src/logging.cpp:107](../../../src/logging.cpp#L107)）：

```
[YYYY-MM-DD HH:MM:SS.mmm]: <级别>: <消息>
 └──────── ① ────────┘  └─ ② ─┘  └── ③ ──┘
```

真实样例（同一台机器上四类典型行）：

```
[2026-01-24 20:13:47.512]: Info: Sunshine version: 0.1.0 commit: a1b2c3d
[2026-01-24 20:13:47.514]: Debug: Expecting incoming session connections from 192.168.1.20
[2026-01-24 20:13:49.901]: Warning: DuplicateOutput1 Failed [0x887a0022]
[2026-01-24 20:13:50.115]: Error: Couldn't find any working encoder matching [nvenc]
[2026-01-24 20:14:02.334]: Fatal: Hang detected! Session failed to terminate in 10 seconds.
```

| 段 | 含义 | 排障价值 |
|----|------|----------|
| ① 时间戳，毫秒精度 | 由 `std::localtime` 格式化，**本地时区** | 唯一能区分"谁先谁后"的信息源；多线程日志交错时全靠它 |
| ② 级别 | `Verbose:`/`Debug:`/`Info:`/`Warning:`/`Error:`/`Fatal:`（另在测试构建里有 `Tests:`） | 决定"这条要不要处理" |
| ③ 消息 | 各模块自己拼的字符串，多数带 `[方括号]` 包裹的关键参数 | 关键参数（编码器名、端口号、IP、错误码）都在这 |

### 1.4 六个级别，以及该怎样对待它们

`sink->set_filter(severity >= min_log_level)`（[src/logging.cpp:177](../../../src/logging.cpp#L177)）是唯一的过滤点，级别数值越小越"啰嗦"：

| 级别 | 数值 | 前缀 | 源码里的注释定义 | 排障时怎么看待 |
|------|:----:|------|------------------|----------------|
| `verbose` | 0 | `Verbose: ` | "Dominating output." | 逐包/逐帧级细节，只在定位疑难问题时临时打开 |
| `debug` | 1 | `Debug: ` | "Follow what is happening." | 状态机、参数、握手细节；**编码参数是否生效看这里** |
| `info` | 2 | `Info: ` | "Should be informed about." | 默认级别；路标行全在这里 |
| `warning` | 3 | `Warning: ` | "Strange events." | 功能仍可用，但行为可能"不标准"（如驱动不支持某特性后降级） |
| `error` | 4 | `Error: ` | "Recoverable errors." | **Sunshine 自己把它定义为"可恢复"** |
| `fatal` | 5 | `Fatal: ` | "Unrecoverable errors." | 真正决定生死的级别，见第 8 章 |

级别定义原文在 [src/logging.cpp:40-45](../../../src/logging.cpp#L40)。

★ 这张表里最容易被忽略的是 `error` 那一行：**Sunshine 认为 `error` 是"可恢复错误"**。所以日志里刷出成百条 `Error:` 并不等于程序要死了；反过来，**没有 `Fatal:` 也可能是"带病启动"**——最典型的就是编码器探测失败：Sunshine 仍然会启动、WebUI 仍能打开，只是客户端连上后黑屏。原因写在代码注释里（[src/main.cpp:441](../../../src/main.cpp#L441)）：

```
// If any of the following fail, we log an error and continue event though sunshine will not function correctly.
// This allows access to the UI to fix configuration problems or view the logs.
```

### 1.5 怎么调级别

- 默认 `min_log_level = 2`（`info`），见 [src/config.cpp:895](../../../src/config.cpp#L895)。
- 两种写法都接受（[src/config.cpp:1944](../../../src/config.cpp#L1944)）：

```ini
min_log_level = debug     # 名称写法
min_log_level = 1         # 数字写法，等价
```

| 你要查的问题 | 建议级别 | 理由 |
|--------------|:--------:|------|
| 连不上、应用启动失败、WebUI 打不开 | `info`（默认） | 路标行全在 info，无需改配置 |
| 编码参数"改了没生效"、会话握手细节 | `debug` | 参数级日志（如 `NvEnc: created encoder ...`）多为 debug，见 [09 §5 自检](./09-NVENC编码参数详解与场景调优.md#5-自检怎么确认参数真的生效了) |
| 配置项"改了没反应" | `verbose` | 有 `config: '<键>' = '<值>'` 逐键回显与自动改写记录 |
| 只想抓崩溃 | `error` 或 `fatal` | 日志小，但会丢掉"崩溃前发生了什么"，一般不建议 |

⚠️ 打开 `debug`/`verbose` 后日志增长很快（每帧、每包都可能有一行），排障结束记得改回 `info`。

⚠️ 调参时不要用 `error` 级别：它会连 `Warning: Unrecognized configurable option [...]` 这类**拼写错误提示**一起吞掉（该提示本身只在 `min_log_level <= 3` 时打印，[src/config.cpp:1975](../../../src/config.cpp#L1975)）。

⚠️ FFmpeg 与 libdisplaydevice 的日志被接到同一个级别上（[src/logging.cpp:165-166](../../../src/logging.cpp#L165)）：`setup_av_logging()` 在 `min_log_level >= 1` 时把 FFmpeg 日志接进来。所以"编码器打开失败"的**真正原因**（FFmpeg 那句）通常就在 `Could not open codec` 附近的上下文里，而它只在 `debug` 及以上级别才出现。

### 1.6 日志还有"看不见的那一半"

| 现象 | 原因 | 位置 |
|------|------|------|
| 控制台有、日志文件里没有 | 日志同时写 `std::cout` 和文件；`logging::init()` **之前**的 `BOOST_LOG` 只进 stdout，不进文件、也不进 WebUI 日志页（源码注释原文：*if anything is logged prior to this point, it will appear in stdout, but not in the log viewer in the UI*） | [src/logging.cpp:172](../../../src/logging.cpp#L172)、[src/main.cpp:263](../../../src/main.cpp#L263) |
| 日志里有、控制台没有 | Windows 服务模式下没有终端 | — |
| 配置项提示只在控制台出现 | `Warning: Unrecognized configurable option [<名字>]` 是直接 `std::cout` 的，不是日志记录 | [src/config.cpp:1977](../../../src/config.cpp#L1977) |
| 文件里的内容比控制台"晚"一点 | sink 是**异步**的，`auto_flush(true)` 保证每条写盘，但后台线程有极小的延迟 | [src/logging.cpp:187](../../../src/logging.cpp#L187) |
| 崩溃前的最后几条日志丢了 | sink 的后台线程在进程被强杀时来不及 flush；`debug_trap()` 之类的强杀路径**之前**都显式调了 `logging::log_flush()` | [src/logging.cpp:258](../../../src/logging.cpp#L258) |

★ 由此得到一条很实用的判据：**"我在配置文件里加了一行，日志里完全没反应"只有两种常见解释**——① 键名拼错，被 `Unrecognized configurable option` 吞在 stdout 里；② 你改的不是 Sunshine 正在读的那份 `sunshine.conf`（多份配置、命令行 `键=值` 覆盖、或服务与手动的实例各读一份）。

## 2. 排障方法论：把日志读成一条时间线

### 2.1 先认这些 `Info:` 路标

Sunshine 有 4 个以上线程在并发写日志，原始顺序是交错的。**不要把日志从头逐行读**，而是先在这些 `Info:` 路标之间画刻度，再往间隔里看细节。

从进程启动到一次会话结束，路标依次是：

| 路标日志 | 位置 | 说明 |
|----------|------|------|
| `Info: Sunshine version: <版本> commit: <提交>` | [src/main.cpp:265](../../../src/main.cpp#L265) | 每次启动的第一行；**排障先确认版本**，很多"行为不一致"是版本差异 |
| `Info: config: '<键>' = '<值>'` | [src/config.cpp:1609](../../../src/config.cpp#L1609) | 配置回显；敏感项显示为 `[redacted]` |
| `Info: Automatically selected config option '<键>' = '<值>'` | [src/config.cpp:1080](../../../src/config.cpp#L1080) | **Sunshine 自己改写了配置**，不是 bug，见 [09 §1.1 生效边界](./09-NVENC编码参数详解与场景调优.md#1-生效边界一个参数要过四道关) |
| `Info: Starting system tray` | [src/main.cpp:504](../../../src/main.cpp#L504) | 主循环已经跑起来（托盘可关，不影响推流） |
| `Info: Found H.264 encoder: <名称> [<实现>]` | [src/video.cpp:3468](../../../src/video.cpp#L3468) | 编码器探测结果；HEVC/AV1 分别是 [3478](../../../src/video.cpp#L3478) / [3489](../../../src/video.cpp#L3489) |
| `Info: New streaming session started [active sessions: <n>]` | [src/rtsp.cpp:703](../../../src/rtsp.cpp#L703) | RTSP 建会话成功（阶段 ②，见 [02 §4](./02-协议与会话生命周期.md#4--首次客户端连接--推流--断开完整时序)） |
| `Info: Creating encoder <编码器名>` | [src/video.cpp:2621](../../../src/video.cpp#L2621) | 真正开始创建编码器实例；后面紧跟 `Color coding:/Color depth:/Color range:` |
| `Info: Streaming bitrate is <n>` | [src/video.cpp:2235](../../../src/video.cpp#L2235) | 实际使用的码率（与客户端请求值的关系见 [04 §1](./04-码率控制与QoS.md#1-码率数字的完整旅程)） |
| `Info: CLIENT CONNECTED` / `Info: CLIENT DISCONNECTED` | [src/stream.cpp:776](../../../src/stream.cpp#L776) / [779](../../../src/stream.cpp#L779) | 控制通道握手成功 / 断开；**推流是否真的开始，看这一行** |
| `Info: Process terminated` | [src/stream.cpp:1378](../../../src/stream.cpp#L1378) | 被串流的应用自己退出了，通常紧跟会话结束 |
| `Info: <ip>: Ping Timeout` | [src/stream.cpp:1331](../../../src/stream.cpp#L1331) | 客户端心跳超时；正常关窗/断网也会打这条，不要一律当故障 |

把上面这些按时间排开，一次健康的会话骨架长这样：

```
[启动]
  Info: Sunshine version: ...            ← ①进程起来
  Info: config: '...' = '...'            ← ②配置生效
  Info: Found H.264 encoder: ...         ← ③编码器可用
[客户端连接]
  Info: New streaming session started [active sessions: 1]   ← ④会话建立
  Info: Creating encoder ...             ← ⑤编码器实例创建
  Info: Streaming bitrate is ...         ← ⑥码率确定
  Info: CLIENT CONNECTED                 ← ⑦控制通道握手完成，画面即将出现
[结束]
  Info: Process terminated               ← ⑧应用退出（或客户端主动断开）
  Info: CLIENT DISCONNECTED              ← ⑨控制通道断开
  Info: <ip>: Ping Timeout               ← ⑩（有时会出现，正常）
```

**排障的核心动作就是找"第一个不该出现的分叉点"**：把出问题那次的日志和上面这张骨架对齐，第一条偏离骨架的行（`Error:`/`Warning:`/缺失的 `Info:`）就是根因所在的位置，再回到 §3~§7 查它的含义。

### 2.2 有两段错误"可以忽略"，别被它带偏

编码器探测阶段会**故意**去试那些注定失败的编码器，因此日志里必然出现一批 `Error:`。源码用两行 `Info:` 把这段夹起来了：

```
Info: // Testing for available encoders, this may generate errors. You can safely ignore those errors. //
   ...（这一段里的 Error/Warning 基本都是探测噪音）...
Info: // Ignore any errors mentioned above, they are not relevant. //
```

（[src/video.cpp:3368](../../../src/video.cpp#L3368) 与 [src/video.cpp:3449](../../../src/video.cpp#L3449)）

这一段的典型"假警报"：

| 出现在探测块里的日志 | 真实含义 |
|----------------------|----------|
| `Info: Trying encoder [<名字>]` | 正在试这个编码器（正常） |
| `Info: Encoder [<名字>] failed` | 这个编码器没通过验证，**换下一个**（正常） |
| `Info: Encoder [<名字>] is not supported on this GPU` | 硬件不支持（正常） |
| `Error: Couldn't find any working encoder matching [<配置里写的编码器>]` | 你指定的编码器不可用，Sunshine 会自动回退到别的（**看后面有没有 `Found H.264 encoder`**） |
| `Error: Could not open codec [<名字>]: <FFmpeg 错误>` | 打开失败的具体原因，多数是驱动/格式问题 |
| `Error: Couldn't find any working encoder that meets HEVC/AV1 requirements` | 想要的编码格式没有可用编码器（见 [09 §8](./09-NVENC编码参数详解与场景调优.md#8-场景推荐配置)） |

★ 判断"编码器到底行不行"，**只看这三个结论行**：`Found H.264 encoder:` / `Found HEVC encoder:` / `Found AV1 encoder:`。哪个没出现，对应的格式就是不可用。

⚠️ 探测块**之外**还有一类 `Fatal:`（[src/video.cpp:3439](../../../src/video.cpp#L3439)）——它出现在探测块结束之后、一个编码器都没选出来时，含义完全不同，见 §3.4。

### 2.3 三个读日志的习惯

1. **先看时间戳的"间隔"，再看内容**。相邻两行如果隔了 10 秒以上，几乎一定发生了超时（心跳、初始 PING、强制关闭都是 10 s 量级）；间隔只有几十毫秒的成簇日志通常是同一事件的展开。
2. **`Fatal:` 之后一定要往后看**。多数 `Fatal:` 后面紧跟一个"后果行"：`return -1` 类的会有一行启动失败提示，`shutdown_event->raise(true)` 类的会让所有服务线程陆续停止（见第 8 章）。
3. **把"最近改过的东西"和第一条异常对齐**。日志里的 `config: '<键>' = '<值>'` 帮你确认"我改的键到底被读进来了没有"；如果这条没出现，问题在配置解析层（§3.3），不在功能层。

### 2.4 症状 → 先看哪一段日志

| 症状 | 先翻的日志段落 | 再看 |
|------|----------------|------|
| Sunshine 起不来 / 一闪而过 | 版本行之前与紧后（§3.1、§3.2） | 配置是否被拒绝、端口是否被占 |
| WebUI 打不开 | `Couldn't start Configuration HTTPS server`（§8.3） | `credentials/` 权限（§4.2） |
| 客户端连不上 / 一直"正在连接" | `New streaming session started` 前后（§4.3） | RTSP 绑定、加密要求 |
| 连上了但黑屏 | `Found ... encoder` 与 `Creating encoder`（§3.4、§5.2） | 采集失败、编码器或显示配置（§6） |
| 有画面没声音 | `There will be no audio`（§5.3） | 音频设备被独占或音频 sink 配置 |
| 卡顿 / 花屏 | 发包相关 warning（§5.4）与 [05](./05-FEC-重传-丢帧与心跳.md) | 网络与 MTU |
| 手柄没反应 | `ViGEmBus`/`libvirtualhid` 相关（§5.5） | 驱动安装状态 |
| 桌面分辨率/刷新率被改坏 | display_device 段（§6） | §9 R3 的回滚步骤 |
| 进程突然消失 | 最后几行 + `Hang detected!`（§8.2） | 崩溃前 10 秒的日志 |

### 3.2 那条"用开始菜单快捷方式启动"的提示到底在说什么

`Fatal: To relaunch Sunshine successfully, use the shortcut in the Start Menu. Do not run Sunshine.exe manually.` 在 Windows 上会从**两个不同位置**打出来。前面那几行不同，但病因是同一个。

**路径 A —— 配置根本没读进来**（判据在 [src/config.cpp:2087](../../../src/config.cpp#L2087)）：

```
Fatal: Failed to apply config: <filesystem 错误>
Fatal: To relaunch Sunshine successfully, use the shortcut in the Start Menu. Do not run Sunshine.exe manually.
```

判据是 `!config_loaded && !shortcut_launch`：

- `config_loaded` = 配置文件成功加载（[src/config.cpp:2075](../../../src/config.cpp#L2075)）；
- `shortcut_launch` = 进程带 `--shortcut` / `--shortcut-admin` 标记（[src/config.cpp:2011](../../../src/config.cpp#L2011)），只有开始菜单快捷方式会带上。

也就是说：**用开始菜单快捷方式启动时，配置读不出来可以"先放着"**（源码注释说明 UCRT64 下非管理员且 `config` 目录尚不存在时会抛 access denied，交给服务实例去建）；**没有快捷方式标记时，配置读不出来就直接放弃启动**（[src/config.cpp:2088](../../../src/config.cpp#L2088) 打出提示、睡 10 秒、`return -1`）。非 Windows 平台没有"快捷方式"这一说，条件退化为只有 `!config_loaded`（[src/config.cpp:2091](../../../src/config.cpp#L2091)）。

**路径 B —— 证书 / 凭据目录建不出来**（[src/main.cpp:466](../../../src/main.cpp#L466) / [469](../../../src/main.cpp#L469)）：

```
Error: Couldn't create directory [<安装目录>\config\credentials] :<系统错误>
Error: Couldn't open [<安装目录>\config\credentials\pkey.pem]
Fatal: HTTP interface failed to initialize
Fatal: To relaunch Sunshine successfully, use the shortcut in the Start Menu. Do not run Sunshine.exe manually.
```

前两条来自 `http::create_creds()`（[src/httpcommon.cpp:168](../../../src/httpcommon.cpp#L168) / [174](../../../src/httpcommon.cpp#L174) / [179](../../../src/httpcommon.cpp#L179) / [184](../../../src/httpcommon.cpp#L184)，共四种写法）；它返回非 0 → `http::init()` 返回 -1（[src/httpcommon.cpp:67](../../../src/httpcommon.cpp#L67)）→ `main()` 打出两条 `Fatal` 并睡 10 秒。

**无论哪条路径，共同点是：双击 `sunshine.exe` 得到的是一个没有管理员权限、且工作目录不对的进程**，于是 `<exeDir>\config\` 下的配置与证书都读不进来。这是安装后"第一次启动就失败"最常见的原因。

处置：用开始菜单里的 Sunshine 快捷方式启动（它会带标记并触发 UAC），或者直接用 Windows 服务（§9 R4 第 2 条）。

### 5.6 心跳与断开：怎么判断"谁先断的"

心跳有双套机制（RTSP 与控制通道），完整说明看 [05 §6](./05-FEC-重传-丢帧与心跳.md#6-心跳双套机制)。日志侧只需记住：

| 日志 | 位置 | 谁断了 |
|------|------|--------|
| `Error: Initial Ping Timeout` | [src/stream.cpp:2122](../../../src/stream.cpp#L2122) | **从没收到过第一个 PING** 就超时 → 客户端连上了但控制通道不通。这是"画面没出来 / 马上断开"的关键信号，通常伴随 §5.4 的端口问题 |
| `Info: <IP>: Ping Timeout` | [src/stream.cpp:1331](../../../src/stream.cpp#L1331) | 会话中后期心跳停了 → 客户端崩溃、断网、锁屏。**正常关闭窗口也会出现**，不要一律当故障 |
| `Info: CLIENT DISCONNECTED` | [src/stream.cpp:779](../../../src/stream.cpp#L779) | 控制通道结束 |
| `Info: Process terminated` | [src/stream.cpp:1378](../../../src/stream.cpp#L1378) | 被串流的**应用**退出了（游戏自己关掉、崩溃） |

★ 断开顺序的判读规则：`Process terminated` 在前 → 应用自己没了；`Ping Timeout` 在前 → 网络/客户端没了；两者都没有但会话结束 → 客户端主动优雅退出。8 条断开路径的判别见 [02 §5](./02-协议与会话生命周期.md#5-断开路径全集)。

## 8. `Fatal` 到底意味着什么

### 8.1 三种后果，差别很大

日志里所有 `Fatal:` 只有三种收场，**分辨它们决定了你要不要"救进程"**：

```
                        Fatal: 出现
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  ① 进程正常结束        ② 被看门狗强杀        ③ 进程不退出
  退出码有意义          logging::log_flush()  fatal 只是措辞
  raise 事件或 return   lifetime::debug_trap() 调用方 return -1
        │                    │                    │
        ▼                    ▼                    ▼
  ✅ 端口 / 配置类        ⚠️ 卡死类            ✅ 只影响这一次会话
  修好配置即可            先杀进程再查 §9 R4     或纯提示，无需处理
```

- **① 进程正常结束**：绝大多数 `Fatal:` 都是这一类。两条路径：一是打日志 → `shutdown_event->raise(true)` → 主循环退出 → 各线程 join → `main()` 返回 `lifetime::desired_exit_code`（正常收尾在 [src/main.cpp:536](../../../src/main.cpp#L536)，若在启动早期就被叫停则走 [src/main.cpp:489](../../../src/main.cpp#L489)），典型例子是 RTSP / HTTP 端口绑定失败（[src/rtsp.cpp:1349](../../../src/rtsp.cpp#L1349)、[src/nvhttp.cpp:1732](../../../src/nvhttp.cpp#L1732)、[src/confighttp.cpp:2408](../../../src/confighttp.cpp#L2408)）；二是 `main()` 或 `config::parse()` 直接 `return -1`，例如配置文件损坏、`HTTP interface failed to initialize`。两者的共同点是**进程正常结束、退出码可信、文件都已落盘**。
- **② 被看门狗强杀**：只有两个来源，都是"10 秒都没关掉"的看门狗（见 §8.2）。`debug_trap()` 在 Windows 上是 `DebugBreak()`（[src/entry_handler.cpp:92](../../../src/entry_handler.cpp#L92)），**是异常终止，不是正常退出**——退出码不可信，且不会执行任何清理。
- **③ 进程不退出**：日志级别写的是 `fatal`，但**没有任何地方去 raise 关闭事件**，函数只是 `return -1` 让调用方失败，或者这条 `fatal` 根本就是一句提示。共三类：`video::probe_encoders()` 找不到可用显示/编码器（[src/video.cpp:3439](../../../src/video.cpp#L3439)，随后主线程只打一条 `Error: Video failed to find working encoder`，进程继续跑）、`stream::start_broadcast()` 的视频/音频套接字初始化失败（见 §8.3，让本次会话起不来、客户端收到 500）、以及 GeForce Experience 的 GameStream 冲突提醒（[src/main.cpp:498](../../../src/main.cpp#L498)，只是**用 `fatal` 级别喊话**，连失败都算不上）。这一类最容易被误判成"程序崩了"。

★ 由此得到一条实用判据：**日志最后一行是 `Fatal:` 且之后什么都没有 → ②；之后还有若干行（线程停止、`Process terminated` 等）→ ①；`Fatal` 之后进程还在、WebUI 还能打开 → ③。**

### 8.2 两种"强制终止"的日志长什么样

**来源 A：进程收到退出信号但 10 秒内没退**

```
Info: Interrupt handler called          ← 或 Terminate handler called
（…… 10 秒内没有正常退出 ……）
Fatal: 10 seconds passed, yet Sunshine's still running: Forcing shutdown
```

出处：[src/main.cpp:395](../../../src/main.cpp#L395) / [415](../../../src/main.cpp#L415)，看门狗在 [src/main.cpp:398](../../../src/main.cpp#L398) / [418](../../../src/main.cpp#L418)。触发方式：Ctrl+C、`taskkill`、服务停止、托盘退出都算。

**来源 B：会话无法在 10 秒内结束**

```
Fatal: Hang detected! Session failed to terminate in 10 seconds.
```

出处：[src/stream.cpp:2219](../../../src/stream.cpp#L2219)。这是**针对 NVENC + Windows HAGS（硬件加速 GPU 计划）死锁的已知规避手段**：让 Sunshine 自己崩掉，这样服务管理器能把它重新拉起来。源码注释就写在上面几行。

看到这一条时的正确动作：**不要把"崩溃"当根因去修**，而是去查它上面 10 秒里的 `video.cpp`/`stream.cpp` 日志（编码器释放卡住、`Starting async encoder teardown` 之后没有 `complete`）。把 HAGS 关掉通常是有效的规避。

★ **另一条极易踩坑的时序**：上表里 `stream.cpp` 那五条 `Fatal` **不会在 Sunshine 启动时出现**。原因是 `broadcast` 对象是"懒加载"的（`safe::make_shared<broadcast_ctx_t>(start_broadcast, end_broadcast)`，[src/stream.cpp:634](../../../src/stream.cpp#L634)），`start_broadcast()` 只在 **`broadcast.ref()` 被调用时**才执行；而在整个启动路径上，`broadcast.ref()` 只有 `session::start()` 一个入口（[src/stream.cpp:2268](../../../src/stream.cpp#L2268)）——另两处（[2139](../../../src/stream.cpp#L2139)、[2166](../../../src/stream.cpp#L2166)）都要等这条会话已经建好之后才轮到。所以：

- 启动日志里**看不到**任何视频/音频端口问题 —— 别因为"启动日志很干净"就排除端口占用；
- 症状必然是"**Sunshine 明明在跑，但一连接就失败**"，且日志里会有 `New streaming session started` 之后紧跟 `Failed to start a streaming session`；
- 同理，`Error: Couldn't bind Control server to port` 也只在第一个客户端连接时出现；
- 反面是好消息：`ref()` 只在成功时把计数置 1，**失败不会被记住**（[src/thread_safe.h:704](../../../src/thread_safe.h#L704) 的 `_count` 检查）。把占用端口的进程关掉后，**往往不必重启 Sunshine**，客户端重新连接一次就会重新执行一遍 `start_broadcast()`；只要每次都失败，说明占用者还在。

## 9. 致命错误回滚手册

按"代价从低到高"分成 6 级（R1~R6）。**从 R1 开始，不要跳级**。

```
R1 配置回滚     改/删 sunshine.conf 相关键，apps.json 重建
R2 状态回滚     清 sunshine_state.json、凭据、配对
R3 显示回滚     display_device 持久化、分辨率/刷新率残留
R4 系统回滚     服务、nvprefs、防火墙、UPnP 映射
R5 版本回滚     换回旧版二进制
R6 源码回滚     git 层面撤销（仅开发者）
```

### R1 · 配置回滚（90% 的 `Fatal` 死在这里）

**触发情形**：`Failed to apply config`、`Fatal: Unknown command`、改完配置后起不来。

第一步是**备份再改**，不要原地反复试：

```powershell
cd "C:\Program Files\Sunshine\config"
Copy-Item sunshine.conf sunshine.conf.bak
```

然后按下面三条之一处理：

1. **只想撤掉刚加的键**：把该键整行删掉或前面加 `#`。注意 `#` 是行内注释符，`键 = 值 # 说明` 是合法的。
2. **想整体回到"最小可用"**：把 `sunshine.conf` 内容清空（或改名，让 Sunshine 重新生成一份默认的），只保留必须的项：
   ```ini
   # 最小可用配置示意
   sunshine_name = Sunshine
   min_log_level = info
   ```
   ⚠️ 清空配置后，**配对关系仍在**（存在 `sunshine_state.json`），但端口/编码器等都会回到默认值。
3. **想临时覆盖而不动文件**：用命令行覆盖，进程退出即失效：
   ```
   sunshine.exe min_log_level=debug port=48989
   ```
   覆盖语法是 `名称=值`（[src/logging.cpp:267](../../../src/logging.cpp#L267)）。**这是最安全的验证手段**：先用命令行确认某个值能解决问题，再决定要不要写进文件。

**应用列表被改坏**（`apps.json` 损坏、应用全丢）：直接删掉 `apps.json`，重启时会从模板重建（[src/config.cpp:1824](../../../src/config.cpp#L1824)）。代价是自定义应用要重加，所以删之前先备份。

**忘了 WebUI 密码**：

```
sunshine.exe --creds 新用户名 新密码
```

（[src/entry_handler.cpp:47](../../../src/entry_handler.cpp#L47) → `http::save_user_creds`）这是唯一有专用命令的恢复项，各打包格式的调用方式见 [docs/troubleshooting.md](../../../docs/troubleshooting.md)。

**想看全部可用命令行**：

```
sunshine.exe --help
```

输出原文（[src/logging.cpp:264](../../../src/logging.cpp#L264)）：

```
Usage: sunshine [options] [/path/to/configuration_file] [--cmd]
    Any configurable option can be overwritten with: "name=value"

    Note: The configuration will be created if it doesn't exist.

    --help                    | print help
    --creds username password | set user credentials for the Web manager
    --version                 | print the version of sunshine

    flags
        -0 | Read PIN from stdin
        -1 | Do not load previously saved state and do retain any state after shutdown
           | Effectively starting as if for the first time without overwriting any pairings with your devices
        -2 | Force replacement of headers in video stream
        -p | Enable/Disable UPnP
```

| 标志 | 排障场景 | 说明 |
|------|----------|------|
| `-1` | "怀疑状态文件导致启动异常" | **不加载也不保存状态**：跳过 `load_state()` 和 `save_state()`（[src/nvhttp.cpp:1612](../../../src/nvhttp.cpp#L1612) / [456](../../../src/nvhttp.cpp#L456)）。⚠️ **不会覆盖已有配对**，是"无菌启动"验证手段，不是清除配对的工具 |
| `-0` | 脚本化配对 | 从 stdin 读 PIN |
| `-2` | 排查花屏/黑屏的首帧问题 | 强制替换视频流的头部 |
| `-p` | 排查外网访问 | 切换 UPnP |

### R2 · 状态与凭据回滚

| 想回滚什么 | 操作 | 影响 |
|------------|------|------|
| 全部配对关系 | 删除 `sunshine_state.json`（或在 WebUI 里 `/api/clients/unpair-all`） | 所有客户端需重新配对 |
| 某个客户端 | WebUI 设备列表里删除/禁用（`/api/clients/unpair`、`/api/clients/update`） | 只影响该设备 |
| WebUI 密码 | `--creds`（见 R1） | WebUI 需重新登录 |
| 证书 | 删除 `config/credentials/` 下的文件 | ⚠️ 需要重新配对；`credentials/` 目录在迁移脚本里被刻意锁过权限（`icacls /inheritance:r`，只给 Administrators 完全控制、Users 只读，见 [migrate-config.bat](../../../src_assets/windows/misc/migration/migrate-config.bat)），删不掉时先看权限 |

⚠️ **不要用"删 `sunshine_state.json`"来解决连接问题**。连接问题先查 §4.3，多数是格式/加密/端口，清配对只会让你多做一遍配对。

### R3 · 显示配置回滚（"桌面分辨率被改坏了"）

这是唯一一类**会影响系统、且必须专门回滚**的状态。三条途径，按优先级：

1. **重启 Sunshine**（通常就够了）。`display_device::init()` 启动时会做崩溃恢复，把上次残留的显示配置还原（[src/main.cpp:297](../../../src/main.cpp#L297)）。
2. **调用专用 API**：
   ```
   POST /api/reset-display-device-persistence
   ```
   对应 `display_device::reset_persistence()`（   [src/confighttp.cpp:1891](../../../src/confighttp.cpp#L1891)、[src/display_device.cpp:898](../../../src/display_device.cpp#L898)），以及托盘菜单里的同款操作（[src/system_tray.cpp:241](../../../src/system_tray.cpp#L241)）。这是**清除"我改过显示设置"这个记忆**，之后 Sunshine 不再尝试还原（也不会再乱改）。
3. **手动改回**：Windows 显示设置 / Linux `xrandr`。如果连桌面都进不去，`display_device.state` 可以直接删除。

配套可调项（避免下次再被改坏）：

| 配置键 | 作用 |
|--------|------|
| `dd.config_revert_on_disconnect` | 断开时是否还原显示配置 |
| `dd.config_revert_delay` | 还原前的延迟（毫秒），显示器切换慢的设备需要调大 |
| `output_name` / `adapter_name` | 固定用哪块屏/哪块 GPU，避免自动选择选错 |

⚠️ 别忘 §6 里那条 warning：客户端**没勾"优化游戏设置"**时，Sunshine 根本不会去改分辨率。所以"分辨率没被改"通常是客户端设置问题，不是回滚失败的证据。

### R4 · 系统集成回滚

| 项目 | 回滚方式 |
|------|----------|
| Windows 服务 | `net stop SunshineService` / `sc delete SunshineService`；重新安装用安装目录下的 `install-service.bat`、卸载用 `uninstall-service.bat`（它们也会顺带清理旧名服务 `sunshinesvc`） |
| 服务启动类型 | 存在 `%LOCALAPPDATA%\LizardByte\Sunshine\service_start_type.txt`，安装脚本据此恢复，不要随手删 |
| 进程卡死 | 先正常结束（`Stop-Process -Id <PID>`），10 秒看门狗本来也会处理；但 ② 类 `Fatal` 之后进程可能已消失，此时检查是否被服务自动拉起 |
| 远程重启（仍需 WebUI 可用） | `POST /api/restart`（[src/confighttp.cpp:2379](../../../src/confighttp.cpp#L2379) → `platf::restart()`，[src/platform/windows/misc.cpp:1313](../../../src/platform/windows/misc.cpp#L1313)）。⚠️ 独立运行（有控制台窗口）时走 `atexit` 重启；作为服务运行时只是退出，由服务管理器拉起 |
| nvprefs（NVIDIA 驱动偏好被改过） | 正常退出会自动还原；异常终止后手动执行 `sunshine.exe --restore-nvprefs-undo`（Windows 专有，[src/main.cpp:92](../../../src/main.cpp#L92) → [src/entry_handler.cpp:63](../../../src/entry_handler.cpp#L63)） |
| 防火墙规则 | Windows Defender 防火墙里删掉 Sunshine 相关的入站规则，重新启动让 Sunshine 重新添加 |
| 路由器 UPnP 端口映射 | 删掉 Sunshine 建的映射项；`-p` 或配置里关掉 UPnP 可阻止它再次建（[src/upnp.cpp:220](../../../src/upnp.cpp#L220)） |
| 过期的配置目录（老版本遗留） | 用 [migrate-config.bat](../../../src_assets/windows/misc/migration/migrate-config.bat) 迁移；⚠️ **脚本结尾会删除旧目录下的 `*.txt` 和 `*.log`**（[第 58–59 行](../../../src_assets/windows/misc/migration/migrate-config.bat#L58)），迁移前先把日志拷走 |

### R5 · 版本回滚

适用场景：升级之后开始出现以前没有的故障，且日志没给出明确原因。

1. **先留证据**：把整个 `config/` 目录（含 `sunshine.log*`、`sunshine.conf`、`sunshine_state.json`）复制出来。
2. **备份当前二进制**，换成旧版本。
3. **配置文件通常可以继续用**：配置系统对未知键只报警告不报错（[src/config.cpp:1977](../../../src/config.cpp#L1977)）。但**新版本自动写入的键**（`Automatically selected config option`）旧版本可能不认识，会以 `Unrecognized configurable option` 提示——这正是该提示存在的意义。
4. **`sunshine_state.json` 一般向下兼容**（就是一份 JSON）；如果旧版本读不了，日志会打 `Couldn't read <路径>: <错误>`，此时删掉它重新配对即可。
5. ⚠️ **`display_device.state` 是版本间最容易出问题的文件**：换了版本后如果显示设置行为异常，直接删掉它（等价于 R3 的第 2 条）。

### R6 · 源码级回滚（开发者）

```
git log --oneline -20                 # 找到引入问题的提交
git revert <提交>                      # 生成一个反向提交，保留历史
```

排查时优先用 `git bisect` 定位；`sunshine.log` 里的 `Info: Sunshine version: <版本> commit: <提交>` 能直接给你"这个 bug 出现在哪个 commit"，省掉一半二分次数。

构建可复现的要点：Windows 上用 msys2 + UCRT64 编译，构建目录以 `cmake-build-` 开头；测试可执行文件是构建目录 `tests\` 下的 `test_sunshine`。

## 10. 一页决策树

遇到问题时照这个顺序走，每一步都有明确的"通过/不通过"判据。

```
① 找到日志
   config/sunshine.log（要历史就 .1~.5）        ── 文件不存在？→ 查权限/是否服务模式（§1.2）
                      │
② 确认版本与配置
   看 Info: Sunshine version: 与 config: 回显    ── 缺 config: 行？→ 配置没被读（§3.2/§3.3）
                      │
③ 对齐健康骨架（§2.1）
   找第一个不该出现的分叉点
                      │
     ┌────────────────┼────────────────┐
     ▼                ▼                ▼
  启动就挂          能起来但连不上      连上了但效果差
  §3                §4                §5 / §6
     │                │                │
     └────────────────┴────────────────┘
                      │
④ 日志里有 Fatal: 吗？
   ├─ 没有 ──► 这不是致命错误。按 §3~§7 对应表处理；多半是 Error/Warning 级功能降级
   └─ 有  ──► 进程还在吗（WebUI 能打开 / 托盘还在）？
              ├─ 还在 ──► ③类"进程不退出"，按 §8.3 归类为 ③ 的那几条处理
              └─ 已经没了 ──► 日志是否到此结束？
                              ├─ 结束（②类被强杀）→ §8.2；先处理卡死/HAGS，再走 R4
                              └─ 后面还有行（①类正常退出）→ 按 §8.3 定位那一条 → 走 R1→R2→R3…
                      │
⑤ 还搞不定？打开 debug
   min_log_level = debug（或用命令行 sunshine.exe min_log_level=debug）
   ★ 先跳过探测块里那两行 Info: 夹起来的 Error（§2.2）
```

## 11. 排障速查清单

**每次报障，先收集这四样**（缺一样都会让定位变慢）：

1. `config/sunshine.log` **以及** `.1`~`.5`（WebUI 只给当前那份，见 §1.2）；
2. `sunshine.conf`（注意把密码类键脱敏）；
3. `Info: Sunshine version:` 那一行原文；
4. 客户端型号 + 编码格式 + 分辨率/刷新率 + 大致时间点。

**五分钟自检清单**：

- [ ] 日志里有没有 `Found H.264/HEVC/AV1 encoder`？没有 → 编码器问题（§3.4）
- [ ] 探测块（`// Testing for available encoders ...` 与 `// Ignore any errors mentioned above ... //` 之间）里的 `Error` 是不是被我当成故障了？（§2.2）
- [ ] 有 `New streaming session started` 吗？有 → RTSP 层没问题，往推流层查（§5）
- [ ] 有 `CLIENT CONNECTED` 吗？没有 → 控制通道没握手，看 `Initial Ping Timeout`（§5.6）
- [ ] 有没有 `Unable to initialize audio capture`？有 → "没声音"已经解释了（§5.3）
- [ ] 有没有 `packetsize is small/large`？有 → 掉线去找 MTU/码率（§5.4）
- [ ] 端口占用类日志是 `Error`（控制口）还是 `Fatal`（视频/音频/RTSP/HTTP 口）？（§8.3）
- [ ] 有 `Fatal:` 吗？有 → 先分清 ① 正常退出 / ② 被强杀 / ③ 进程不退出（§8.1）
- [ ] 我最近改过什么？改动和第一条异常的**时间顺序**对得上吗？
- [ ] 需要更细的信息吗？`min_log_level = debug` 复现一次（§1.5）

**回滚动作速查**：

| 症状 | 最短路径 |
|------|----------|
| 改配置后起不来 | R1：删掉刚加的键，或命令行 `键=值` 先验证 |
| 忘了 WebUI 密码 | R1：`sunshine.exe --creds <用户> <密码>` |
| 应用列表空了 | R1：备份后删 `apps.json`，重启重建 |
| 配对诡异 | R2：`-1` 无菌启动验证；确认是状态问题再清 `sunshine_state.json` |
| 桌面分辨率改坏 | R3：重启 → `POST /api/reset-display-device-persistence` → 手动改回 |
| 进程卡死/连不上又关不掉 | R4：结束进程、重启服务；查看门狗那两条 `Fatal`（§8.2） |
| NVIDIA 驱动设置被改坏 | R4：`sunshine.exe --restore-nvprefs-undo` |
| 升级后才出问题 | R5：换回旧版本，保留新旧两份 `config/` 对比 |

---

## 12. 小结

- 日志只有三段：**时间戳 / 级别 / 消息**。级别里 `Error` 是"可恢复"，`Fatal` 才决定生死；而 `Fatal` 本身有三种收场——① 进程正常结束、② 被看门狗强杀、③ 进程根本不退出（第 8 章），分不清就会把"端口占用"当成"程序崩溃"。
- 排障不是逐行读，而是**先在 `Info:` 路标之间画刻度，再找第一个偏离健康骨架的分叉点**；探测块（`Testing for available encoders` … `Ignore any errors mentioned above`）里的 `Error` 是噪音。
- 判断编码器只看 `Found H.264/HEVC/AV1 encoder` 三行结论。
- 回滚遵循 R1→R6 的阶梯：**先动配置，再动状态，再动显示，最后才动程序和系统**。命令行 `键=值` 和 `-1` 是两级"零损伤探针"，先用它们定性再动手改文件。
- 收尾提醒：排障结束把 `min_log_level` 改回 `info`，并注意 `sunshine.log` 只保留 5 份历史。
