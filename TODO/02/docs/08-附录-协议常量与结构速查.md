## 1. 端口与服务速查

所有端口都由 `config::sunshine.port`（默认 **47989**）加上一个**偏移量**得到，计算公式为 `net::map_port(port) = (uint16_t)(config::sunshine.port + port)`（[src/network.cpp:245](../../../src/network.cpp#L245)）。

| 服务 | 常量 | 偏移 | 默认端口 | 传输 | 明文/加密 |
|------|------|:----:|:--------:|------|-----------|
| GameStream HTTPS（nvhttp） | `nvhttp::PORT_HTTPS`（[src/nvhttp.h:52](../../../src/nvhttp.h#L52)） | −5 | **47984** | TCP | TLS（自签证书） |
| GameStream HTTP（nvhttp） | 基准端口（无偏移） | 0 | **47989** | TCP | 明文 |
| WebUI HTTPS（confighttp） | `confighttp::PORT_HTTPS`（[src/confighttp.h:29](../../../src/confighttp.h#L29)） | +1 | **47990** | TCP | TLS（同一张证书） |
| 视频流（stream） | `stream::VIDEO_STREAM_PORT` | +9 | **47998** | UDP | 可选 AES-GCM |
| 控制通道（stream） | `stream::CONTROL_PORT` | +10 | **47999** | UDP | 可选 AES-GCM（V2 信封） |
| 音频流（stream） | `stream::AUDIO_STREAM_PORT` | +11 | **48000** | UDP | 可选 AES-CBC |
| RTSP 协商（rtsp） | `rtsp_stream::RTSP_SETUP_PORT`（[src/rtsp.h:15](../../../src/rtsp.h#L15)） | +21 | **48010** | TCP | 明文 RTSP（媒体本身另加密） |

**端口校验**：`config::sunshine.port` 必须落在 `[1024 + nvhttp::PORT_HTTPS, 65535 - rtsp_stream::RTSP_SETUP_PORT]` 区间内（[src/config.cpp:1895-1901](../../../src/config.cpp#L1895-L1901)），即 `[1019, 48010]`。

**辅助端口 / 协议**

| 用途 | 机制 | 备注 |
|------|------|------|

## 2. 控制通道（UDP :control）

### 2.1 消息类型总表

控制通道的载荷前置一个 4 字节头（`control_header_v2`：`uint16 type` + `uint16 payloadLength`），`type` 取自下表。表中「索引」为 [src/stream.cpp:40-55](../../../src/stream.cpp#L40-L55) 的 `IDX_*` 常量，「线上值」为 [src/stream.cpp:57-74](../../../src/stream.cpp#L57-L74) 的 `packetTypes[]`。

| 索引 | 线上值 | 名称 | 载荷结构 | 方向 |
|:----:|:------:|------|---------|------|
| `IDX_START_A`=0 | `0x0305` | Start A | 无（裸控制头） | 主机 → 客户端 |
| `IDX_START_B`=1 | `0x0307` | Start B | 无 | 主机 → 客户端 |
| `IDX_INVALIDATE_REF_FRAMES`=2 | `0x0301` | Invalidate ref frames | `int32[4]`（`firstFrame`、`lastFrame`、保留×2） | 客户端 → 主机 |
| `IDX_LOSS_STATS`=3 | `0x0201` | Loss Stats | `int32[4]`：`framesLost`、`packetsLost`、`packetsTotal`、`periodMs` | 客户端 → 主机 |
| 4 | `0x0204` | Frame Stats | —— | **未使用**（仅占索引位） |
| `IDX_INPUT_DATA`=5 | `0x0206` | Input data | `NV_INPUT_HEADER` + 具体输入包（见 §5） | 客户端 → 主机 |
| `IDX_RUMBLE_DATA`=6 | `0x010b` | Rumble data | `control_rumble_t` | 客户端 → 主机 |
| `IDX_TERMINATION`=7 | `0x0109` | Termination | `control_terminate_t` | 双向（主机退出时发 `0x80030023`） |
| `IDX_PERIODIC_PING`=8 | `0x0200` | Periodic Ping | 通常无载荷 | 双向 |
| `IDX_REQUEST_IDR_FRAME`=9 | `0x0302` | IDR frame | 无 | 客户端 → 主机 |
| `IDX_ENCRYPTED`=10 | `0x0001` | fully encrypted | `control_encrypted_t` 信封，内层再是上述任一类型 | 双向 |
| `IDX_HDR_MODE`=11 | `0x010e` | HDR mode | `control_hdr_mode_t` | 主机 → 客户端 |
| `IDX_RUMBLE_TRIGGER_DATA`=12 | `0x5500` | Rumble triggers ⟵ Sunshine 扩展 | `control_rumble_triggers_t` | 客户端 → 主机 |
| `IDX_SET_MOTION_EVENT`=13 | `0x5501` | Set motion event ⟵ Sunshine 扩展 | `control_set_motion_event_t` | 客户端 → 主机 |
| `IDX_SET_RGB_LED`=14 | `0x5502` | Set RGB LED ⟵ Sunshine 扩展 | `control_set_rgb_led_t` | 客户端 → 主机 |
| `IDX_SET_ADAPTIVE_TRIGGERS`=15 | `0x5503` | Set adaptive triggers ⟵ Sunshine 扩展 | `control_adaptive_triggers_t` | 客户端 → 主机 |
| `IDX_SET_PLAYER_LEDS`=16 | `0x5504` | Set player indicator LEDs ⟵ Sunshine 扩展 | `control_set_player_leds_t` | 客户端 → 主机 |

> **索引 4 是空洞**：`IDX_INPUT_DATA` 直接跳过 4，因为 `packetTypes[4]`（`0x0204` Frame Stats）在 GameStream 中早已废弃，Sunshine 保留数值以对齐客户端的 `packetTypes` 数组下标（客户端按**下标**而非值来校验）。
>
> **头长度随方向而变**：客户端 → 主机的 V1 报文只有 2 字节 `type`（`NVCTL_ENET_PACKET_HEADER_V1`），只有 `0x0001` 信封的内层才是完整的 4 字节 `NHCTL_ENET_PACKET_HEADER_V2`。所以 `parse_control_packet()` 只剥掉 `sizeof(type)`（[src/stream.cpp:642-657](../../../src/stream.cpp#L642-L657)）——这也正是 `IDX_ENCRYPTED` 的回调要用 `payload.data() - 2` 反推 `control_encrypted_t` 起点的原因。两个方向的剥离细节见 [03 §3.1](./03-输入系统.md#31-两条输入协议0x0206-与-0x0001的分层剥离)。

### 2.3 加密信封

```
control_encrypted_t（8 B 前缀）
┌────────────────┬────────────┬──────────────────────┬───────────────┐
│ encryptedHdrTy │  length    │        seq           │  GCM tag(16B) │
│ u16 = 0x0001   │  u16       │       u32            │  + 内层报文    │
└────────────────┴────────────┴──────────────────────┴───────────────┘
         │
         └─ seq 同时是 AES-GCM 的 IV 来源：
              V2（controlProtocolType == 13）: IV = 12 字节 seq 字节序 + 'H' + 'C'
              旧版                           : IV = 16 字节，iv[0] = seq（低 8 位）
```

| 场景 | IV 构造 | 源码 |
|------|---------|------|
| 主机发出加密控制消息 | `seq++` → 12 B `seq` **+** `'H'` `'C'` | `encode_control<>()`，[src/stream.cpp:570](../../../src/stream.cpp#L570) |
| 主机**接收**加密控制消息 | 12 B `seq` + `'C'` `'C'`（V2）或 16 B legacy，`iv[0] = seq` | `controlBroadcastThread`，[src/stream.cpp:1160+](../../../src/stream.cpp) |
| 旧版明文输入（`IDX_INPUT_DATA` 走 legacy AES-GCM） | `legacy_input_enc_iv` 链式传递，BE `int32` 长度前缀 | 同上 |

### 3.3 `fecInfo` 与 `multiFecBlocks` 位域

`fecInfo`（32 位，小端整数打包）：

```
 fecInfo = (x << 12) | (data_shards << 22) | (percentage << 4)
            │                │                       │
            │                │                       └─ 分片使用的 FEC 百分比（8 位）
            │                └───────────────────────── 本块数据分片数（10 位）
            └────────────────────────────────────────── 本块内分片下标（低位起，10 位）
```

`multiFecFlags = 0x10`（恒定为标准 multi-FEC 标志）。

`multiFecBlocks = (blockIndex << 4) | ((fec_blocks_needed - 1) << 6)`

`streamPacketIndex = (lowseq + x) << 8`，其中 `x` 为分片下标、`lowseq` 为会话内递增序列基址（`rtp.sequenceNumber = BE(lowseq + x)`）。

### 3.4 加密与 IV

| 项目 | 规则 |
|------|------|
| 算法 | AES-128-GCM |
| IV | 12 字节递增计数器 `gcm_iv_counter`（64 位），**`iv[11]` 固定为 `'V'`** |
| 认证标签 | 16 字节，落在 `video_packet_enc_prefix_t::tag` |
| 启用条件 | `session->config.encryptionFlagsEnabled & SS_ENC_VIDEO` |
| FEC 与加密顺序 | **先加密再分片**，因此校验分片保护的是密文 |

**B. 会话相关端口**

端口值本身见 §1，与一次会话绑定的只有四个：控制通道 `+10`（ENet，双向）、视频 `+9`（UDP）、音频 `+11`（UDP）、RTSP 协商 `+21`（TCP）。三个 UDP 流都**按客户端来源 IP:port 建立映射**，而不是按端口号区分会话——所以同机多会话时端口号完全相同，靠 `_peer_to_session` / `peer_to_*_session` 区分。

**C. 三套独立的「10 秒」**

| 机制 | 判定对象 | 默认值 | 超时后果 | 出处 |
|------|---------|:------:|---------|------|
| ENet 控制通道超时 | 控制通道有无任何事件 | `ping_timeout`，默认 `10 s` | 打印 `<地址>: Ping Timeout` → `session::stop()`（[src/stream.cpp:1329-1334](../../../src/stream.cpp#L1329-L1334)） | §7.3、[05 §6.1](./05-FEC-重传-丢帧与心跳.md#61-机制-a控制通道-enet-超时保活判定) |
| UDP 每流首包 PING | 视频 / 音频流是否收到首包 | 同上（首包到达前用 `pingTimeout` 兜底） | 不认领该会话，`recv_ping` 超时返回错误 | [05 §6.2](./05-FEC-重传-丢帧与心跳.md#62-机制-budp-每流初始-ping发现客户端端口--建-qos) |
| 会话终止看门狗 | `session::join()` 是否按时返回 | `10 s`（硬编码） | `Hang detected! Session failed to terminate in 10 seconds.` → `lifetime::debug_trap()`（[src/stream.cpp:2218-2222](../../../src/stream.cpp#L2218-L2222)） | §7.2 |

三者互不代替：控制通道活着但 UDP 没到，会话照样没画面；UDP 正常但控制通道断了，`session::stop()` 会终止整场会话；而看门狗管的是**关**会话这一步。另外 RTSP 侧还有一个事件超时（[05 §6.3](./05-FEC-重传-丢帧与心跳.md#63-机制-c补充rtsp-侧的事件超时)），它管的是配对 / 启动阶段的等待，与会话内的这三套 10 秒无关。展开分析见 [05 §6.4](./05-FEC-重传-丢帧与心跳.md#64-三重超时速查)。

## 13. 全篇要点回顾

> 与 §12 互补：§12 列**反直觉**结论，本节按「端口 → 报文 → 结构 → 常量 → 机制」压缩成 8 条主干。

1. **端口全部由 `sunshine.port` 派生**，偏移 `−5 / 0 / +1 / +9 / +10 / +11 / +21`，基准默认 `47989`。
2. **控制通道有两套编号**：客户端按 `packetTypes[]` 的**数组下标**校验（`IDX_*`），线上传输的是**值**（`0x0305` 等）；`IDX_*` 4 号位是废弃空洞。
3. **控制通道的加密信封自描述**：`control_encrypted_t` 的信封类型恒为 `0x0001`（`IDX_ENCRYPTED` 的线上值），内层 `seq` 同时充当 IV 来源，V2 用 `'H''C'`/`'C''C'` 区分收发方向。
4. **输入 magic 存在三处数值碰撞**（`0x09`、`0x0A`、`0x0D`），必须结合 `NV_INPUT_HEADER::size` 长度消歧，不能只按 magic 判定类型。
5. **视频 FEC 块数上限 4**，超限就整帧跳过 FEC；音频 FEC 固定 4+2 且校验矩阵被硬编码成 Nvidia OpenFEC 的值。
6. **心跳有两套且互相独立**：ENet 控制通道靠「任意事件刷新超时」，UDP 每流靠「首包 PING 认领会话」。
7. **`max_bitrate` 只在 AVCodec 路径生效**，NVENC 路径直接用客户端码率（见 [04](./04-码率控制与QoS.md)）。
8. **队列满时默认整队清空**（`drop_oldest` 的 `_queue.clear()`），这是延迟优先策略的直接体现。
